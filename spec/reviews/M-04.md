## 3. The key ruling that must survive (M4-R1)

### M4-R1 — M-04's replacement of the client order key. **Essential — confirmed, and it is the only replacement case in the product.**

**Confirmed explicitly, so that no later cycle "harmonises" it away with M-03's stable-key rule:**

> **A stock rejection is a definite server statement that no order was created for that key. An edit made after a lost or ambiguous response proves nothing.** That is the whole distinction. M-03 keeps the key because the server may already hold an order for it; M-04 replaces the key because the server has said, in a response the device actually received and read, that it holds nothing for it. The two rules are not in tension: they are the same principle — never create a second order, never let a real order be swallowed as a duplicate — applied to the two things the device can know.

M-04 §5.7's two reasons are ruled correct and stand as written: no duplicate is possible (the old key corresponds to no order), and reusing the old key risks a server answering the reduced order with the cached rejection or discarding it as a duplicate, which would lose a real order.

**Two wording problems, both Essential to fix, because both now read as the deleted blanket rule:**

1. **§5.7's opening citation** — "This follows G-04 §7.7 (the key is replaced whenever a cart line changes)" — cites a rule that no longer exists. Rewritten to: *"The key is stable for the whole checkout session and is replaced in exactly one case, this one (G-04 §7.7): the server has definitively stated that no order was created for it. A stock rejection is that statement; a lost or ambiguous response is not, which is why M-03 never replaces the key."*
2. **§5.7's "Back to cart" paragraph** — "When the guest then removes the lines on G-03, that cart change replaces the key under G-04 §7.7 — the same end result by the other path" — is now **false**: under the corrected rule a cart change replaces nothing, so the B02 route would carry the rejected key into the next submission, which is exactly the case §5.7's second bullet warns against.

**Ruling on the trigger — the simplest rule that closes the B02 gap:** the key is replaced **when M-04 opens**, in the same step that writes the out-of-stock marks (§3.1), and for the same stated reason — it records a fact the server stated, not a decision the guest has made. Concretely:

- §3.1's "on opening, before any tap" paragraph gains: *"In the same step, the client order key is replaced with a new one and M-03's attempt count is reset to 0, because the rejection is the server's definite statement that no order exists for the old key (§5.7)."*
- §5.6 step 3 ("Replace the client order key and reset M-03's attempt count") is **deleted** — it already happened on open.
- §5.7's "Back to cart" paragraph is rewritten to: *"'Back to cart' (B02) needs no key rule of its own: the key was already replaced when M-04 opened, so every route out of this modal — B01, B02, the backdrop, browser back, and even a browser reload — reaches the next submission with a fresh key. No path exists from a stock rejection to a resubmission under the rejected key."*
- Acceptance criterion 14 becomes: *"After B01, the next submission attempt carries a client order key different from the one the server rejected, and M-03's attempt count starts again at 1 on a later failure."* (unchanged in substance; the replacement simply happened earlier.)
- Acceptance criterion 15 is rewritten: *"After B02 and removal of the lines on G-03, the next submission attempt likewise carries the key that was installed when M-04 opened, not the rejected one; no cart change is relied on to replace it."*
- New acceptance criterion: *"Reloading the browser while M-04 is open, or leaving by the backdrop or browser back, still leaves the device holding the new key: the rejected key is never sent again."*

This keeps one rule instead of two, removes the only branch in which a rejected key could survive, and is consistent with everything M-03 now says.
