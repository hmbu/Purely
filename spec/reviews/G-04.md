## 3. Rulings on the five Critical findings

### R1 — Critical 1 (F9, Persona 4b): single-digit room numbers. **Essential.**

**Reason:** a hotel with a room "7" is ordinary, and the 2-digit minimum silently converts it into an invented value ("07", "70") that can be a *different real room* — a wrong-room delivery, which is the operational-error bar exactly.

**Ruling (binding, and it is a three-line change):**

1. F01's accepted length becomes **1 to 5 digits**, counted after trimming. §7.1 "Length" row is rewritten as: *"Minimum **1** digit, maximum **5** digits, counted after trimming. The bounds cover rooms '1' through '99999'."* The sentence "Single-digit room numbers are not accepted in version 1" is deleted.
2. The **"too short" error message is deleted** from §7.1's message table and from §7.6's priority order. With a minimum of 1, the only remaining short case is an empty field, which already has its own message ("اكتب رقم غرفتك / Enter your room number"). Three messages remain: empty, wrong characters, too long.
3. §5.3 loses the "typing 2–5 digits costs two seconds" clause (it now reads 1–5).
4. Acceptance criterion 14 is rewritten to assert the opposite of what it asserts today:
   *"Typing '7' into F01 and blurring shows no error; submitting with '7' hands the string '7' to M-01, which displays it as '7'."*
   Criteria 15, 16 and 18 change "2–5" to "1–5" wherever the bound is named.
5. **Cross-file:** the 2-digit minimum is restated in **M-01 §6.2** ("guarantees a room number of 2–5 digits") and **M-03 §7.1** ("2–5 Western digits"). Both become 1–5. No other behaviour on those files changes.
6. Leading zeros still stay exactly as typed (D5), so "07" and "7" remain two distinct room labels — which is now harmless, because the guest with room 7 can type 7.

### R2 — Critical 2 (F10, Persona 4c): alphanumeric room numbers. **Later, and recorded as OQ-01.**

**Reason:** whether the target hotel uses letters or separators is a fact about the real hotel that nobody in this project has, so it cannot be settled here; what can be settled is that the limitation stops being silent.

**Ruling:**

1. **For version 1 as specified, digits-only stands.** No letter support, no second field, no "room qualifier", no prompt toward the notes field is added to G-04 in this cycle.
2. The question, the proposed alternative (accepted character set, length bound, keyboard) and the exact list of what must change in G-04 §5.3 / §7.1 and in M-01 if the answer is "yes" are written in **`/spec/open-questions.md` as OQ-01**, which this review creates. The decision is needed before G-04 is built, not before it is approved.
3. G-04 must state the limitation where a reader of the spec will meet it. Add to **§5.3**, immediately after the "Validation against a list of real hotel rooms" paragraph, one recorded-limitation paragraph (spec prose, not guest copy):
   *"**Recorded limitation (open question OQ-01).** Version 1 accepts digits only. A hotel whose room labels contain letters or separators ('A-12', '12B') cannot be served by this field as specified, and the guest sees a wrong-character error that reads as if they mistyped. This is a known, recorded limitation, not an oversight; it is resolved by OQ-01 before build."*
4. The **guest-facing** copy does not change: no message on G-04 tells the guest their hotel is unsupported (v1 does not know whether it is).
5. The feature itself — letters and separators in F01 — goes to `/spec/backlog.md` as **G-04-L6**, blocked on OQ-01.

### R3 — Critical 3 (F8, Persona 4a): M-01 cannot catch a confident typo. **Essential in its cheap part only; the rest is recorded.**

**Reason:** re-reading your own typo is a thin net, but every thick net (room list, directory, lookup, second confirmation) is backend work or friction charged to every single order to catch a rare case.

**Ruling:**

1. **Rejected outright for version 1:** validation against a list of real rooms, a room directory or picker, any server lookup while typing, and any second confirmation step after M-01. None of these may appear in the revision. (Room-list validation is deferred, not lost: backlog **G-04-L5**.)
2. **The cheap part that is Essential — a cross-screen requirement, binding on G-05 and G-06 when they are written:** the guest must **meet their room number again after submitting, while cancelling is still possible**. Concretely:
   - **G-05 Order submitted** shows the room number prominently: its own line, the number at **24 px bold or larger**, Western digits, leading zeros kept, in the same format M-01 used. Ruled copy: `سيُوصَّل طلبك إلى الغرفة {room}` / `Your order will be delivered to room {room}`.
   - **G-06 Order tracking** shows the same line in the order's details, and while the status is **New** it is visible in the same view as the "Cancel order" control, so a guest who reads a wrong number has the repair in front of them. Same ruled copy.
   - Neither screen may show the room number only inside a collapsed section, a footer, or a line smaller than the order number.
3. **G-04's own duty:** none beyond §5.3, which already states plainly that M-01 plus cancel-while-New is the v1 protection. It must additionally point at the new post-submit sighting, one sentence in §5.3: *"After submission the room number is shown again on G-05 and on G-06, where it stays readable while the order is still New and can be cancelled (locked decision 6)."*
4. The residual risk that survives all of this — a guest who is confidently wrong and does not read the number on any of the three surfaces — is recorded in **OQ-01**, with the room-list alternative, so it is a known accepted risk rather than an unexamined one.

### R4 — Critical 4 (F14, Persona 5): nothing says the order was not sent after M-04. **Essential.**

**Reason:** a guest who believes they ordered and walks away, while staff received nothing, is a silently broken journey; the cure is one line of text.

**Ruling — new element G-04-C13:**

| Property | Decision |
|---|---|
| ID / type | **G-04-C13** — content block, one notice line, full width minus the 16 px section padding, 14 px text, preceded by the same 16 px "!" circle icon used by the error texts, dark text on a light-gray fill, 8 px rounded corners, 12 px inner padding. It is **not** an error (no field is wrong) and **not** a toast (G-01 convention bans toasts): it does not fade, does not auto-dismiss, and has no close control. |
| Placement | Directly **under the header S01 and above the order summary S02**, with 16 px below it. It is the first thing in the scroll area, and G-04 is scrolled to the top on the M-04 return (§3.1 already says so), so it is on screen without any scrolling. |
| Copy (Arabic) | `لم يتم إرسال طلبك بعد. راجع الملخص ثم اضغط «إرسال الطلب».` |
| Copy (English) | `Your order has not been sent yet. Review the summary, then tap "Submit order".` |
| When shown | On the render of G-04 that follows **M-04 "Remove them and continue"** when the cart still has at least one line. |
| How long it stays | Until **M-01 opens** (a validation pass on B05). It does not disappear on a timer, on scroll, or on any field edit. It is shown again if a later M-04 sends the guest back again. |
| Survives reload | **Yes.** A one-bit "awaiting resubmission" flag is stored with the checkout draft (§7.7) and cleared when M-01 opens or when the draft is discarded — because a guest who reloads the tab in this exact state is the guest most likely to believe the order is already on its way. |
| Not shown after M-03 | **Correct and deliberate.** M-03 is the failure modal and its own copy ("لم نتلقَّ تأكيدًا… / We have not received confirmation…") already says the order was not sent; a second notice under the header would be a duplicate message for the same fact. |

Also: §3.1's M-04 row currently ends "no toast; the shorter summary and the new total are the feedback". Rewrite it to: *"no toast; C13, the shorter summary and the new total are the feedback"*. §5.7's "no toast, no snackbar" line stays true and is not weakened — C13 is a persistent notice, not a transient one.

New acceptance criterion (R4): *"After M-04 'Remove them and continue' leaves at least one line, G-04 shows C13 under the header with the exact copy above; C13 stays visible through scrolling, field edits and a browser reload, and disappears only when M-01 opens."*

### R5 — Critical 5 (F17, Persona 6): the client order key defeats duplicate-safe retry. **Essential — and decision D13 as written is wrong.**

**Reason:** §7.7's "replace the key whenever any order value changes" protects against resubmitting a stale room number, but it opens a worse hole: a guest whose response was lost, who double-checks one field before retrying, silently creates a second real order. Two real deliveries for one intended order is the operational error this screen exists to prevent, and M-03 §5.5 rule 4 currently writes that hole down as acceptable.

**Ruling — one contract spanning three files. Write it once in G-04 §7.7 and have M-01 and M-03 reference it.**

**G-04 §7.7 — "Client order key" bullet, rewritten in full:**

1. The key is generated **once**, the first time B05 opens M-01 in this checkout session, and is stored with the checkout draft.
2. **The key is never replaced because a value changed.** It stays stable for the whole checkout session, across: a cart change made via "Edit cart" or the back arrow, M-01 "Edit room number" and any subsequent edit of the room number, any edit of the notes, a change of payment method, any edit of the amount, M-03 "Close" and every retry, M-04 "Remove them and continue", and a browser reload of G-04. Every attempt in one checkout session carries the same key.
3. The key identifies **the attempt**, not the values. The server contract (behaviour rule for the technical team, already written in M-01 §7.3 layer 5 and now the single source of it): *if an order already exists for this client order key, the server returns that existing order as a success, with its order number and its contents, and never creates a second one. It does not merge, update, or overwrite the existing order with the newly submitted values.*
4. Therefore **the order the guest gets back may differ from what they just submitted.** That is the intended outcome: the guest is shown the order that actually exists (G-05, then G-06) instead of a second one being created. M-01 applies such a response exactly like a first-time success (M-01 §7.4 is unchanged, and its criterion 18 already covers it).
5. The guest's repair path, when the returned order is not the one they wanted, is **cancel while the status is New** (locked decision 6, M-02 from G-06) and then place a fresh order — which is a fresh checkout session with a new key. This is why R3's requirement that **G-05 and G-06 show the room number prominently** is part of this contract and not a separate nicety: it is how the guest discovers that the existing order carries the old value.
6. The key is **discarded only** on (a) a successful submission, together with the draft, when G-05 opens; or (b) the cart becoming empty (the §3.1 guard, or M-04 removing the last line), which ends the checkout session. Closing the tab discards it with the draft.

**M-01 — changes required:** §7.3 layer 4 currently restates the replacement rule ("is replaced by G-04 whenever any order value changes afterwards") and its "Changed order" bullet. Both are rewritten to the stable-key contract: a changed order submitted under the same key returns the existing order rather than creating a new one, and M-01 treats that as a success. Layer 5 (the server rule) is unchanged and is now cited from G-04 §7.7. Acceptance criterion 25's second half ("after B02 and a change to the room number, the new M-01 instance carries a different key") is rewritten to: *"after B02 and a change to the room number, the new M-01 instance carries the **same** key."*

**M-03 — changes required:** §5.5 rule 3's last sentence ("If the guest changes any order value first, G-04 replaces the key and resets the attempt count") is deleted. **§5.5 rule 4, the "accepted limitation", is deleted in full** — the limitation no longer exists. §7.2 and §5.3's threshold rule change "reset to 0 when the key is replaced" to "reset only when the key is discarded (success, or the cart empties)". Acceptance criterion 14 is rewritten to: *"After 'Close', changing any order value and submitting again sends the **same** client order key; if the earlier attempt had already created an order, G-05 shows that order and no second order exists."*

**G-04 — acceptance criteria:** criterion 42 is rewritten to the opposite assertion: *"Changing a cart line, the room number, the notes, the payment method or the amount after M-01 was opened once does **not** change the client order key; every M-01 opening in the same checkout session carries the same key."* Criterion 41's second half stays true (a new checkout after G-05 does not reuse the previous key). Add one criterion: *"If the server already holds an order for this key, confirming a submission that differs from it results in G-05 showing that existing order and exactly one order on the server and on the device."*
