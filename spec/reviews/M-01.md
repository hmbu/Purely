## 3. Rulings on the three Critical findings

### R1 — F-KEY-1: the stable key can silently discard a corrected room number. **Essential, and it amends ruling R5 of `/spec/reviews/G-04.md`.**

**Reason:** the tester is right. A stable key plus a server rule that returns the stored order "as a plain success" means a guest who corrects the room number after an ambiguous failure is shown G-05 as if the correction went through, while the order on file still carries the mistake — the exact operational error this modal exists to prevent, produced by the fix for a different one.

**The refined contract (binding; written once in G-04 §7.7, referenced by M-01, M-03 and G-05):**

1. The client order key stays **stable for the whole checkout session**, exactly as R5 ruled. Nothing about rules 1, 2, 5 and 6 of G-04 §7.7 changes: the key is created the first time B05 opens M-01, is never replaced because a value changed, and is discarded on success or when the cart empties.
2. **The server never creates a second order for a key it has already fulfilled.** Unchanged.
3. **The server's response now has three kinds, not two** (behaviour rule for the technical team):
   - `created` — no order existed for this key; the submitted order was created. Plain success.
   - `existing-identical` — an order already existed for this key and the submitted payload is the same order (same lines, quantities, room number, payment method, amount and notes). Plain success; the guest never learns two requests were made.
   - `existing-different` — an order already existed for this key and **the submitted payload differs from it**. The server returns the stored order **marked as already existing**, together with the stored order's room number and status. It does **not** merge, update or overwrite the stored order, and it does **not** create a second one.
4. **What M-01 does with the third kind.** M-01 renders nothing new and gains no element: it runs the success sequence of §7.4, with two corrections that apply to `existing-identical` and `existing-different` alike:
   - **The order record saved on the device is the order the server returned** — its order number, its lines, its room number, its payment method, its amount, its total, its time — never the payload M-01 just sent.
   - **The record's status is the status the server returned** (New, or Accepted & preparing, or any later status from locked decision 5), defaulting to **New** only when the response carries no status. The current text, which always writes New, is wrong for an order the hotel has already accepted.
   Then, as today: the cart is emptied, the draft, the key and the pending-submission record of R2 are discarded, G-04 is dropped from the history, and **G-05 opens**. Emptying the cart is deliberate here too: a cart left behind would be checked out again under a *new* key and would create the real duplicate this contract exists to prevent.
5. **Where the guest is sent: G-05, in an "already existing" variant.** No new modal, no branch to G-06, no change to map §4 decision 6. M-01 hands G-05 one extra flag (`already-existing`) alongside the record; **M-01 owns no copy for this case** — it shows no message of its own (§6.3, §6.4 stay true).
6. **The copy, ruled here and owned by G-05** (one persistent notice line, directly under the room-number box C04 and above C05, 14 px, with the same "!" circle icon convention, never a toast, no close control). `{room}` is the room number of the order that exists, formatted exactly as C04 shows it:
   - Arabic: `طلبك السابق وصل إلى الفندق بالفعل ولم يتغيّر. الطلب المسجَّل هو للغرفة {room}. لتغييره، ألغِ الطلب من صفحة المتابعة ما دام الفندق لم يقبله بعد، ثم أرسل طلبًا جديدًا.`
   - English: `Your earlier order already reached the hotel and was not changed. The order on file is for room {room}. To change it, cancel it from the tracking page while the hotel has not accepted it yet, then place a new order.`
7. **The repair path is cancel-while-New** (locked decision 6, G-06 → M-02), which is why R3 of the G-04 review put the room number on G-05 and G-06 in the first place. A correction is therefore never lost in silence: the guest is either deduplicated correctly (`existing-identical`) or told exactly what exists and what to do about it (`existing-different`).
8. **§7.5 now has four buckets, not three**, and the "no fourth bucket" promise is kept: `created` → G-05; `existing-identical` → G-05; `existing-different` → G-05 with the flag; stock rejection → M-04; everything else (no connection, timeout, server error, malformed) → M-03. A response that is marked already-existing *and* reports unavailable lines is handled as **already existing**: the stored order is the fact, and the stock rejection describes a submission that was never created.

### R2 — F-6.2: closing the tab mid-request destroys the key and opens a real duplicate. **Essential.**

**Reason:** the one interruption most likely on a weak connection is the one the spec does not walk through, and it is the only remaining path that produces two real deliveries for one intended order.

**Ruling — the key and the minimum needed to recognise the attempt are device-scoped, not tab-scoped:**

1. A **pending-submission record** is written on the device (the same storage as the cart and the order list, not the tab-scoped draft storage) **at the moment M-01 sends its request** — that is, in the same synchronous step as the in-flight lock of §7.3 layer 1, before the response can arrive.
2. **What is stored, and nothing more:** the client order key; the time of the first send for that key; the room number string as sent; the order total; and the number of cart lines. The room number, total and line count are there so a human reading device state can recognise the attempt; nothing in version 1 displays them, and no guest-facing element is added by this ruling.
3. **It survives** a closed tab, a browser restart, a tab the browser or OS discards, and a reload. It is **not** part of the checkout draft (G-04 §7.7), whose tab-scoped lifetime and no-pre-fill purpose are unchanged.
4. **A new checkout session adopts the key of an unresolved pending record** instead of generating a new one: when G-04 creates a key (first B05 tap opening M-01), it first checks the device for an unresolved pending-submission record and, if one exists, uses that key. This is the whole fix — the guest who force-closed the tab and orders again submits under the same key, so either the server creates the order (the first request never arrived) or it returns the order that exists, marked already existing, and R1's copy tells the guest what happened.
5. **It is cleared** exactly when: (a) a response of kind `created`, `existing-identical` or `existing-different` is applied (§7.4 step 3, with the draft and the key); or (b) the guest explicitly ends the checkout session by emptying the cart (the G-04 §3.1 guard, "−" to zero on G-03, or M-04 removing the last line); or (c) **24 hours after the first send**, because a key from a previous day describes an order the hotel has long since delivered or cancelled and staff can see on their own screens. A stock rejection (M-04) and a failure (M-03) do **not** clear it — those are exactly the attempts that must stay recognisable.
6. **Residual risk, recorded not built:** a guest who force-closes the tab *and* empties the cart before ordering again discards the record by their own action and can still produce a duplicate. This is recorded in `/spec/open-questions.md` OQ-01's residual-risk section as a third item; no machinery is added for it.

### R3 — F-4.2: the guard is passive; nothing forces the guest to compare the digits. **Essential in its cheap part only; everything else is rejected.**

**Reason:** locked decision 2 asks for a confirmation, not a quiz; every enforcement mechanism taxes every order to catch a rare slip that only the guest's own attention can catch.

**Ruling:**

1. **Rejected outright for version 1:** re-typing the room number to confirm, a room picker or directory, an "I have checked the number" checkbox, a countdown longer than the 300 ms arming delay, and any second confirmation step after M-01. None may appear in the revision. (Room-list validation stays deferred as backlog **G-04-L5**.)
2. **The Essential part is already in the file and must stay exactly as it is:** the number alone on the card at 64 px bold with nothing above 18 px beside it (§5.2, §7.6); no total, payment method, notes or item count competing with it (§5.4); the number visible for the whole loading state; the digits read one at a time by a screen reader. This is the concrete meaning of "large type" and M-01 must not trade any of it away.
3. **The recovery path is real and already ruled:** G-05 shows the room number at 48 px with the wrong-number sentence C05, and G-06 shows it beside "Cancel order" while the status is New (G-04 review R3). M-01 adds nothing; it may cite them in §5.4 in one sentence so a reader of this file sees where the second and third sightings are.
4. **The residual risk is recorded, not engineered away:** `/spec/open-questions.md` OQ-01 already carries it as residual risk 1. M-01 gains one prose sentence in §5.4 pointing at it, so the limitation is visible to whoever reads this modal in isolation.

## 7. What the Thinker must change in this cycle

Exact rulings. Copy is given in both languages wherever copy changes; nothing here is a suggestion.

**R1 — The client order key contract, third response kind, and the saved status.**
- Rewrite **§7.3 layer 4** in full: the key is created once per checkout session, is handed over unchanged, is **never replaced because a value changed**, and M-01 never creates, changes or discards it. Delete the "Changed order → new key" bullet. Keep the "Same order, sent again" bullet.
- Rewrite **§7.3 layer 5** (the server rule) as R1 point 3: three response kinds — `created`, `existing-identical`, `existing-different` — with the rule that the server never creates a second order for a fulfilled key and never merges, updates or overwrites the stored order with the newly submitted values.
- Rewrite **§7.4 step 1**: the record saved on the device is **the order the server returned** (its number, lines, room number, payment method, amount, total, time) and its **status as returned**, defaulting to New only when the response carries no status. Delete the assumption that the status is always New.
- Add to **§7.4**: when the response kind is `existing-different`, steps 1–5 run unchanged and M-01 hands G-05 the record **plus an `already-existing` flag and the returned room number**. M-01 renders no message, no variant and no new element; §6.3 and §6.4 stay true.
