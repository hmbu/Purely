## 3. Rulings on the two Critical findings

**F1 — [Critical, Persona 6] The retryable variant offers no path to G-07 or G-06, so a guest can lose the cancel-before-acceptance window while retrying an unrelated catalog request.**
**F2 — [Critical, Persona 7] The same gap is absolute in the invalid-link variant, which has no Retry to succeed through.**
**Verdict on both: Essential.** The product-manager reasoning, recorded here as the ruling's basis: G-07 and G-06 render entirely from the device and need no catalog, so a catalog failure must never consume the cancel-before-acceptance window that locked decision 6 grants the guest. A guest who cannot cancel a still-New order because an unrelated request is failing is an operational error at the hotel's door, not an inconvenience.

They are one gap and they get one fix.

### Ruling R1 — the element, exactly

1. **ID:** `G-08-B03`. It is a new row in the elements table; the total becomes **10 elements (3 buttons, 0 fields, 5 content blocks, 2 sections)**.
2. **Type:** text button, label 16 px, no icon, tap area at least 44 × 44 px — the same treatment as B01 on the opposite edge. No icon is used, because G-08 has no icon set of its own and its text floor is 14 px.
3. **Label, character-for-character the same string as G-01-B02** (never a new string):
   - Arabic: `طلباتي`
   - English: `My orders`
4. **Placement, identical on both variants:** inside the header S01, at the **end edge** — the left edge in Arabic (RTL), the right edge in English (LTR) — vertically centred, 16 px from the edge. B01 keeps the start edge. The header then holds exactly two controls and nothing else: still no hotel name, no title, no back arrow, no cart bar.
5. **The precise condition under which it is shown:** B03 is rendered **if and only if the device order list holds at least one readable record**, using the same readability test as G-07 §6.3 case 2. The test is evaluated on arrival and again on every re-render (a language switch, a failed Retry), and it is synchronous — it reads the device and sends nothing.
   - When the device holds **zero** readable records, or the storage cannot be read at all, **B03 is not rendered** — not disabled, not greyed, not present. Neither variant shows it.
   - The condition is **the existence of a record, not its status**: a device holding only Delivered or Cancelled orders shows B03 too. G-08 does not read statuses.
   - The condition is identical on the retryable and the invalid-link variant, and it does not change while the screen is shown except by the re-render rule above.
6. **What it does on tap, including with several orders on the device:** it opens **G-07 My orders**, at the top of the list, exactly as G-01-B02 does — **always the list, never a single order and never G-06 directly**, even when the device holds exactly one record, and even when one record is active. One destination, no status read on G-08, and G-07 already sorts newest-first and opens any order with one tap.
7. **Interaction with a Retry in flight:** tapping B03 while the trying state is running navigates to G-07 and abandons the attempt; the catalog response, whenever it arrives, is discarded and never navigates the screen (this extends §5.4 rule 8 from "a late response" to "a response whose screen the guest has left"). B03 is never disabled, including during the trying state. B02 does not change appearance because of B03.
8. **Leaving and coming back:** G-07 has its own URL, so the tap is a normal navigation that pushes a history entry above the URL whose load failed; G-08 still has no URL of its own and the address bar is still never written by G-08. Back from that G-07 returns to the URL whose load failed and loads it again — on success the guest lands on the screen for that URL (G-01, G-02 or G-03), on failure G-08 is shown again as a **fresh visit**, with C04 hidden again on the retryable variant.
9. **Rejected in advance, and recorded so it cannot return in a smaller form.** G-08 gets **no order status, no order count, no badge, no order number, no date, no total, no active-order banner and no deep link to G-06**. §7.4's rule stands with one exact amendment: G-08 still renders **no value** supplied by the server or the device; the *existence* of at least one saved record is the only device fact that reaches this screen, and the only thing it can change is whether B03 is rendered.
10. **Acceptance criteria:** add the six criteria listed in §7 R1, and amend criteria 9 and 23.
