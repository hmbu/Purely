The Thinker acts only on this file. Anything not listed here is unchanged.

**Standing product-manager correction applied throughout this review.** The client order key rule has been corrected since M-03 was written. The final rule, which this review treats as binding and which supersedes the rule quoted inside M-03:

> The key identifies a **submission attempt** and **stays stable for the whole checkout session**, across every edit, retry, modal and reload. The server never creates a second order for a key it already holds. If the resubmitted payload is **identical**, the server returns that order and the app treats it as a plain success. If the payload **differs**, the server still creates nothing and returns the stored order **marked as already existing**; the guest is then shown the order that actually exists, told plainly that their earlier order reached the hotel, with the room number it carries, and that it was not changed, with cancel-while-New as the repair path. The key survives a closed tab (device storage, not tab-scoped) and is discarded only on success or when the cart empties.

M-03's §5.3, §5.5 rules 3–4, §7.2, §3.1 closing sentence and acceptance criterion 14 all restate the superseded rule and are ruled below.

**Alignment with `/spec/reviews/M-01.md` (written in the same cycle).** That review's ruling **R1** states the same contract and names the three response kinds `created`, `existing-identical`, `existing-different`; it also **rules the exact bilingual copy for G-05's already-existing notice and assigns ownership of that copy to G-05**. This review uses those names and does **not** write a competing string: where M-03 meets the third kind, it hands G-05 the flag and G-05 shows the copy already ruled in `/spec/reviews/M-01.md` R1 point 6. One point is refined here rather than repeated — the attempt-count reset (M3-R1 item 3) — because M-01's review was written without M-04's key replacement in view; see §6.2 item 4.

M-03 has **one job: let the guest retry safely.** Every item that would give it a second job is rejected on that ground alone.

## 3. Rulings on the two Critical findings

### M3-R1 — Critical 1 (M-03 F1): four places in this file still specify the superseded key rule. **Essential.**

**Reason:** the file a technical team builds from still tells them to replace the key on an edit, which is precisely the behaviour that turns a lost response plus one cautious correction into a second real delivery — the operational error this modal exists to prevent.

**Ruling (binding; each item is an exact edit):**

1. **§5.5 rule 3, last sentence** — "If the guest changes any order value first, G-04 replaces the key (G-04 §7.7) and resets the attempt count." — **deleted**. Rule 3 is rewritten to: *"After 'Close', the key is kept with the draft. Whatever the guest does next on G-04 or G-03 — change the room number, the notes, the payment method, the amount, or the cart — the next 'Submit order' → M-01 → 'Confirm and send' carries the **same** client order key, because the key identifies this checkout session's submission attempt and not the values it carries (G-04 §7.7). That path is therefore exactly as duplicate-safe as Retry."*
2. **§3.1's closing sentence** — the clause "which reuses the same key **because nothing changed**" is the superseded framing. Rewritten to: *"…the guest then taps 'Submit order' → M-01 → 'Confirm and send', which carries the same client order key, whether or not anything was changed in between (G-04 §7.7)."*
3. **§7.2 Attempt count** — "reset to 0 when the key is replaced" is rewritten to: *"reset to 0 only when the key is replaced by M-04 on a stock rejection, or discarded (a successful submission, or the cart becoming empty). An edit to the order never resets it, so the count follows the guest's real run of failures across edits."*
4. **§5.3's threshold paragraph** — the sentence "it resets to 0 whenever the client order key is replaced (the order changed)" is rewritten to match item 3, and the paragraph gains one clause: *"because the key is stable, a guest who edits something between two failures keeps their count and still meets the reception line on the third failure."*
5. **Acceptance criterion 14** is rewritten to assert the opposite of what it asserts today: *"After 'Close', changing any order value (cart line, room number, notes, payment method, amount) and submitting again sends the **same** client order key; if the earlier attempt had already created an order at the hotel, no second order is created and G-05 shows the order that exists."*
6. **§5.5 rule 2** ("the key cannot change while M-03 is open") stays, and gains the clause *"and it does not change after it closes either"*.

This is the same contract already ruled in `/spec/reviews/G-04.md` **R5**; M-03 restates it, it does not re-decide it.

### M3-R2 — Critical 2 (M-03 F2): nothing specifies "same key, different payload". **Essential.**

**Reason:** the corrected rule makes this case reachable — the guest edits the order after an ambiguous failure and submits, or retries the edited payload while the server already holds the earlier one — and with no stated rule the build team either shows the guest a success for an order that does not match what they just confirmed, or throws the edited order away silently. Both reach the door as the wrong delivery.

**Ruling — the submission response now has three kinds, and M-03 must classify all three:**

| Response kind (names per `/spec/reviews/M-01.md` R1) | What it means | What M-03 does |
|---|---|---|
| **`created`** | The server created the order for this key | M-03 closes, G-05 opens. Unchanged from §6.4 |
| **`existing-identical`** | The server already held an order for this key and the resubmitted payload is the same order | M-03 closes, G-05 opens with that order's number. **Indistinguishable from `created` for the guest**, and deliberately so: there is exactly one order and it is the one they confirmed. §6.4's existing last sentence covers this case and is kept, scoped to identical payloads |
| **`existing-different`** | The server already held an order for this key; the resubmitted payload differs (the guest corrected something after an ambiguous failure). The server created nothing and returned the stored order marked as already existing | M-03 closes and G-05 opens **with that stored order**, and passes G-05 the `already-existing` flag together with the stored order's room number and status. M-03 shows **no copy of its own** for this case |

**M-03 owns none of the explanatory copy. Ruled deliberately and for simplicity:** M-03's job is to let the guest retry safely; explaining that an *earlier* order already exists, with the room number it carries and the cancel-while-New repair, is a statement about an order that now exists and therefore belongs on the screen that shows existing orders. Putting it on M-03 would mean writing it twice (M-01 can receive the same response) and would give the failure sheet a second job. The copy is ruled below as a binding cross-screen requirement on **G-05**, exactly as `/spec/reviews/G-04.md` R3 ruled G-05/G-06 copy before those files existed.

**M-03's own duties, to be written into the file:**

1. §5.4's outcome table gains the three success kinds as one row split in three, with the classification above, and states that all three end the in-flight state as a success.
2. §5.5 gains a new **rule 4** (replacing the deleted one, M3-R3 below) reading: *"**Retry always sends the byte-identical payload of the last attempt**, so Retry itself can meet `existing-different` only when an earlier attempt in this session carried a different payload (the guest edited the order after a failure, submitted, and failed again). In that case the server returns the order it already holds; M-03 treats it as a success, closes, and hands G-05 the stored order plus the `already-existing` flag, the stored order's room number and its status. M-03 never creates, merges, or overwrites an order, and it never re-sends under a new key."*
3. §6.4 keeps its current text for the `existing-identical` case and gains: *"On `existing-different`, G-05 is opened with the stored order and the `already-existing` flag; the guest is told there, not here, that the earlier order already reached the hotel and was not changed."*
4. New acceptance criteria:
   - *"A retry answered `created` or `existing-identical` ends on G-05 showing that order, with no notice of any kind; exactly one order exists on the server and one on the device."*
   - *"A retry answered `existing-different` ends on G-05 showing the **stored** order and passing G-05 the `already-existing` flag with the stored order's room number and status; M-03 adds no copy of its own and no second order is created."*

**Cross-screen — the copy is already ruled and M-03 must not restate it.** The guest-facing notice for `existing-different` lives on **G-05** and its exact bilingual wording is ruled in `/spec/reviews/M-01.md` **R1 point 6** (one persistent notice line under G-05's room-number box, 14 px, "!" circle icon, no toast and no close control, `{room}` being the room number of the order that exists). M-03 writes none of that copy; it only hands over the flag, the stored order, its room number and its status. Any later revision that finds itself writing a second version of this sentence on M-03 has taken a wrong turn.

### M3-R3 — the "accepted limitation" (§5.5 rule 4). **Remove.**

**Reason:** the limitation no longer exists. It described a second order created because an edited resubmission carried a new key; under the corrected rule the key never changes on an edit, the server creates nothing for a key it already holds, and the guest is shown the order that exists. A paragraph telling the technical team to accept a duplicate delivery would, if left in place, be read as permission to build the very behaviour the correction removes.

**Ruling:**

1. **§5.5 rule 4 is deleted in full** — the whole "Accepted limitation, stated so it is not mistaken for an oversight…" paragraph, including the sentence "the hotel receives both orders with the same room number and staff resolve it at the door" and the closing "No device-side detection of this case exists in version 1."
2. **What replaces it:** the new rule 4 written in M3-R2 item 2 — the stable key plus the three-kind response contract, whose outcome for exactly the scenario the deleted paragraph described is now: *no second order is created; the guest is shown the order that exists, told on G-05 that their earlier order reached the hotel and which room it carries, and repairs it by cancelling while the status is New (locked decision 6) and ordering again.*
3. Nothing about this is an "accepted limitation" any longer, so no replacement risk paragraph is written. The one residual — a guest who cancels and re-orders spends a minute doing so — is the ordinary repair path of locked decision 6 and needs no note.
