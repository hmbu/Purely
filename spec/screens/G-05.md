# G-05 — Order submitted (تم إرسال طلبك)

Author: Thinker (Agent 1)
Status: **Draft** (status is changed only by the orchestrator in `/spec/screens-map.md`)
Governing documents: `/CLAUDE.md` locked decisions 1, 2, 3, 4, 6, 7; `/spec/screens-map.md` §2.2 (G-05 row), §2.3 rules 1, 3, 5 and 6, §4 decision 6 (G-05 exists as a separate screen "so the room number and order number are shown once, clearly, before tracking begins"); `/spec/screens/M-01.md` §7.4 (the saved order record G-05 renders from, and the guarantee that it exists on the device before G-05 is drawn); `/spec/screens/M-03.md` §6.4 (the second way to reach G-05); `/spec/screens/G-04.md` §7.1 (leading zeros in the room number are kept), §7.4 (the cash amount is a whole number); conventions set by `/spec/screens/G-01.md` (Western digits 0–9 in both languages; currency format "45.00 ر.س" / "SAR 45.00"; tap area of at least 44 × 44 px; browser zoom and text scaling never disabled; no toast anywhere in version 1; the five status labels in G-01 §5.2).

**Why this screen shows the room number large.** G-04 §5.3 decided the room number is not checked against a list of real rooms, so "305" typed as "350" passes every rule. M-01 makes the guest read the number once *before* sending. G-05 is the second, cheap half of the same protection: the guest meets the number again *right after* sending, at the only moment when the mistake still costs nothing — the order is in status New and can be cancelled from G-06 (locked decision 6). Every element on G-05 is placed so that this number is the first thing the eye lands on after the success mark, and the way to act on a wrong number is written one line beneath it.

---

## 1. ID and name

- **ID:** G-05
- **Name:** تم إرسال طلبك / Order submitted
- **Type:** Full guest screen. It has its own URL, which carries the order number (§3.3). It is shown exactly once per order in the normal flow, immediately after the server accepted the submission.
- **Language:** the language currently saved on the device (locked decision 7; map §2.3 rule 6). G-05 has no language toggle. RTL in Arabic, LTR in English; the room number and the order number are laid out left-to-right, digit by digit, in both languages (M-01 §1 rule).

---

## 2. Purpose

Tell the guest that the order was sent, show the room number it will go to and the order number it carries, and hand the guest to tracking or back to the store.

---

## 3. Entry and exit points

### 3.1 Entry (how the guest arrives)

| From | Trigger | What G-05 receives | What G-05 shows on arrival |
|---|---|---|---|
| M-01 Confirm room number | A success-side response of any of the three kinds `created`, `existing-identical`, `existing-different` to "تأكيد وإرسال / Confirm and send" (M-01 §7.4) | The order record M-01 just saved on the device (§5.0): order number, order time, room number string, lines, notes, payment method, amount or none, total, and **the status the server returned**. On `existing-different` **only**, one extra value is handed over with it: the **`already-existing` flag** | The success state (§6.4), scrolled to the top. G-04 and M-01 are already gone from the history (M-01 §7.4 step 4). The cart is already empty (M-01 §7.4 step 2). C09 is rendered only when the `already-existing` flag was handed over (§5.2) |
| M-03 Order not sent | A success-side response of any of the same three kinds to "إعادة المحاولة / Retry" (M-03 §6.4) | The same record and the same flag, handed over by the same rules | Identical to the row above. On `created` and `existing-identical` the record carries the order the server returned and G-05 shows it as a first-time success, with no notice; on `existing-different` C09 is shown |
| Browser reload on G-05, or browser forward after back went to G-01 | Browser load | Nothing is handed over; G-05 reads the order number from its URL and looks for that record on the device (§3.3) | The success state rendered from the device record, **without C09** (the flag is a hand-off, not part of the record, §5.2); or, if no record exists on this device for that number, G-01 (§3.3) |

There is no other entry. G-06, G-07 and G-01 never lead to G-05 (map §2.2). G-05 sends **no request** on any entry: everything it shows is in the device record, and the server has just answered.

### 3.2 Exit (where each action leads)

| Action on G-05 | Destination |
|---|---|
| Tap "متابعة الطلب / Track order" (B02) | G-06 Order tracking for this order number. G-06 **replaces** G-05 in the history (§3.3), so back from G-06 goes to G-01 exactly as the map's G-06 row says; G-05 is never returned to |
| Tap "العودة إلى المتجر / Back to store" (B03) | G-01, list scrolled to the top, cards all showing "Add", no cart bar, and the active-order banner showing this order (G-01 §3.1 "G-05" row). The history is reset so G-01 is the only entry (the same rule as G-03 "Continue shopping") |
| Tap the back arrow (B01) or browser back | G-01, exactly as B03. The checkout of an already-sent order is never shown again (map §2.3 rule 3) |
| Browser reload | See §3.3 |

G-05 never leads to G-02, G-03, G-04, G-07 or any modal.

### 3.3 URL, reload, forward, and history

- **URL.** G-05's URL carries the order number (example: `…/order/1042/sent`). A modal has no URL (map §2.3 rule 2); a screen does, and this one needs it so a reload can find the record.
- **History on arrival.** When G-05 opens, the history is: G-01 → G-05. G-04 and M-01 are gone (M-01 §7.4 step 4). G-03 and G-02, if they were beneath G-04, are removed too: back from G-05 goes to G-01 and nowhere else.
- **"Track order" replaces G-05.** Tapping B02 replaces the G-05 entry with G-06, so the history becomes G-01 → G-06. Reason: G-05 is a one-time confirmation; returning to it from tracking would show a "sent" message about an order that may already be On the way or Cancelled. Because of this rule **G-05 cannot be reached by browser back from G-06**; that case does not exist.
- **Reload on G-05.** The page reloads and G-05 reads the order number from the URL. If the device holds a record with that number (locked decision 4: orders live on the device), G-05 renders the success state from it, identical to the first render, with no request. If the device holds **no** such record (another device, cleared browser storage, a typed URL), G-05 has nothing true to say and **redirects to G-01** at the top of the list, with no message. Reason: an order number without its device record is not this guest's order as far as the interface can know (no login), and a blank confirmation screen would be worse than the store.
- **Browser forward** from G-01 after back went from G-05 to G-01: the browser returns to G-05's URL; the same reload rule applies (rendered from the device record, or G-01 if the record is gone).
- **Reload never re-sends anything**: the checkout draft, the client order key and the pending-submission record were all discarded when the success-side response was applied (M-01 §7.4 step 3), so there is nothing to resend and no key left for a later checkout to adopt.
- **Offline.** G-05 needs no connection to render; a reload while offline still shows the success state from the device record (the browser's own offline page is outside this spec, as on every screen). "Track order" leads to G-06, which handles the offline case itself (G-06 §6.3).

## 5. Content

### 5.0 What G-05 reads, and from where

G-05 renders **only** from the order record M-01 §7.4 step 1 wrote to the device. It reads these fields and nothing else:

| Field in the record | Used by |
|---|---|
| Server order number | C06; the URL (§3.3); the handoff to G-06 |
| Room number string, exactly as returned by the server and saved (leading zeros kept, G-04 §7.1) | C04, and `{room}` in C09 |
| Total | C07 |
| Payment method ("card" / "cash") | C08 |
| Amount (whole number) or none | C08 |
| **Status, as the server returned it** (M-01 §7.4 step 1) | The visibility of C05 only (§5.2). The status itself is never printed on G-05 |

Plus one value that is **not** part of the record and is handed over only by M-01 or M-03 at the moment G-05 opens: the **`already-existing` flag**, which decides whether C09 is rendered (§5.2).

Not read by G-05: the lines, the product names, the notes, the order time. They are one tap away on G-06 (§5.5).

G-05 **fetches nothing from the server**. The record was written from the server's own success response a moment ago; a second request would add a loading state and a failure case to a screen whose job is to say "done".

### 5.1 Header (S01)

- The header holds the back arrow B01 at the start edge and nothing else. The title C01 is in the body, under the success mark, because the title *is* the message and belongs next to the mark; a second, smaller copy in the header would say the same thing twice.
- No language toggle, no "My orders" button (map §2.3 rule 6; G-01 §5.1).

### 5.2 The room number (C03, C04, C05) and the already-existing notice (C09) — placement, size, and reason

- **Placement:** directly under the title, before anything else about the order. It is the first data on the screen, above the order number, because the order number is a reference the guest may never need, while a wrong room number sends the order to a stranger's door.
- **Size:** 48 px bold in an 88 px box spanning the inner width. The next largest text on G-05 is the title at 22 px, so the room number is at least **2 × the size of anything else** and the largest thing on the screen. Letter-spacing 0.08 em keeps a leading zero visibly its own digit (M-01 §5.2). Five digits at 48 px measure about 175 px, so the number never wraps or shrinks in the 358 px box.
- **Why 48 px and not M-01's 64 px:** M-01 has one job and nothing competes with the number. G-05 must also carry the order number, the total, the payment line and two buttons; at 64 px the box would push the buttons below the fold on a 390 × 664 px viewport. At 48 px every element fits above the buttons on that viewport with the buttons fully visible (§7.5).
- **Label C03** reuses M-01-C02 word for word: "سيُوصَّل طلبك إلى الغرفة / Your order will be delivered to room". The guest read this sentence on M-01 seconds ago; reading it again with the same number is the check.
- **C05** is the action half of the safety requirement: "رقم الغرفة غير صحيح؟ يمكنك إلغاء الطلب من صفحة المتابعة ما دام الفندق لم يقبله بعد / Wrong room number? You can cancel the order from the tracking page until the hotel accepts it". It is a sentence, not a link: the action it points to is B02, the primary button, two elements below. It is shown for every order whose status is New, not only when something looks wrong, because the interface cannot know when the number is wrong.
- **C05 is suppressed when the record's status is past New** (Accepted & preparing, On the way, Delivered, Cancelled). Reason: cancellation is available only before staff accept the order (locked decision 6), so printing the promise after acceptance would send the guest to G-06 for a control that is not there. Nothing replaces the suppressed sentence — no substitute copy is invented here — because the true state of the order is one tap away on B02, which is the same destination C05 pointed at. When C09 is shown and C05 is suppressed, the notice line stands alone under the room number.
- **C09, the already-existing notice, and when it appears.** M-01 and M-03 hand G-05 the record together with an `already-existing` flag when, and only when, the server's response was of kind `existing-different` — the guest submitted a changed order under a key for which the hotel already held one, so nothing was created and the stored order was returned marked as already existing (G-04 §7.7 rule 4). In that case C09 is rendered as one persistent line directly under the room-number box C04 and above C05, at 14 px, with the "!" circle icon, no close control and no toast. Its exact copy is in §4 and is byte-identical to the copy reproduced in the contract at G-04 §7.7 rule 5; **G-05 owns this string and it is written nowhere else as guest copy** — M-01 and M-03 render no version of it.
  - The room number the guest reads at 48 px in C04 is the room number of the order that exists, because the saved record is the order the server returned (M-01 §7.4 step 1); `{room}` in C09 is that same string. The guest therefore sees the room the hotel will actually deliver to, and the notice says plainly that the change they just made was not applied.
  - On `created` and `existing-identical` no flag is handed over, C09 is not rendered, and G-05 says nothing about how many requests were made.
  - **The flag is a hand-off, not part of the order record**, so a reload of G-05 renders the same screen without C09. This is a decision, not an omission: the notice describes what happened during one submission, while the record describes the order; the guest who reloads is looking at the order that exists, with its room number at 48 px, and the repair path is still B02. The status, which *is* in the record, keeps governing C05 across a reload.
- The value is shown exactly as saved: "0305" stays "0305" (G-04 §7.1). Western digits; no "#", no "Room" prefix inside the box.
- Contrast: digits on the box at least 7:1; all other text on G-05 at least 4.5:1 (M-01 §5.2 rule). The digits are read by a screen reader one at a time ("zero three zero five").

### 5.3 Order number (C06)

- "رقم الطلب {order number} / Order number {order number}", number in 20 px bold. The number is the server's order number as stored in the record, printed exactly; G-01's banner and G-06 print the same string (G-01 §5.2).
- It is smaller than the room number on purpose (§5.2) but larger than the body copy, because it is the one thing the guest may need to tell a staff member.

### 5.4 Total and payment (C07, C08)

- C07 "الإجمالي {total} ر.س / Total SAR {total}", total from the record with two decimals per G-01 §7.2; currency label from store settings.
- C08, one of three variants, chosen by the record's payment method and amount:

| Record | Arabic | English |
|---|---|---|
| card | الدفع عند الاستلام: بطاقة | Pay on delivery: Card |
| cash, no amount | الدفع عند الاستلام: نقدًا | Pay on delivery: Cash |
| cash, amount N | الدفع عند الاستلام: نقدًا — ستدفع بـ {N}.00 ر.س | Pay on delivery: Cash — you will pay with SAR {N}.00 |

- The amount is the whole number the guest typed (G-04 §7.4), shown with two decimals to match every other amount ("200.00 ر.س" / "SAR 200.00").
- Reason these two lines exist: the guest is about to open the door to a staff member who expects payment; the total and the method are what the guest needs to have ready. Both come straight from the record, add no request and no state.

### 5.5 What is deliberately not on this screen

Each item was considered and left out because G-05 has one job (map §4 decision 6): show the room number and the order number once, clearly, then hand off.

- **No item count and no line list.** The guest just reviewed the lines on G-04; the count adds nothing actionable, and the list is on G-06 one tap away.
- **No estimated delivery time.** No store setting or server field for it exists in version 1, and a time the hotel did not commit to is an operational error waiting to happen. If the product manager wants one, it belongs in `/spec/backlog.md`.
- **No notes echo.** Notes are on G-06's details block.
- **No order time.** On G-06.
- **No status label.** The record carries the status the server returned, which is usually New but may already be later (M-01 §7.4 step 1); G-05 reads it only to decide whether C05 is shown (§5.2) and never prints it, because a status word here adds something for the guest to interpret on a screen whose job is "done". G-06 owns the status.
- **No "save this page" or "your order is stored on this device" notice.** The "My orders" button on G-01 and the active-order banner make the order findable without instruction.
- **No cancel button.** Cancelling lives on G-06 only (G-01 §5.2 rule, map §4 decision 8 spirit: one place per action). C05 tells the guest where.
- **No toast, no confetti, no animation** on the success mark. No language toggle, no hotel name, no "My orders" button.

## 6. States

G-05 has exactly one rendered state: **success**. The other three template states are unreachable, with the rule that makes them so.

### 6.1 Loading

**Unreachable.** G-05 sends no request (§5.0) and reads a record that M-01 §7.4 guarantees exists before G-05 is drawn. On a reload, reading the device record is immediate. There is no skeleton, no spinner, no placeholder on G-05.

### 6.2 Empty

**Unreachable.** A record always has an order number, a room number, a payment method and a total (M-01 §7.4 step 1). The only "nothing to show" case is a reload with no matching record on the device, and that case never renders G-05: it goes to G-01 (§3.3).

### 6.3 Error

**Not rendered.** No request means no request failure. A missing record on reload is handled by the redirect in §3.3, with no message. There is no typed input, so there is no field error.

### 6.4 Success

Triggered by: every entry in §3.1 that finds the record.

On screen, top to bottom: S01 with B01; C02 success mark; C01 "تم إرسال طلبك / Order submitted"; C03 label; C04 room number at 48 px; **C09 already-existing notice, when the flag was handed over**; C05 wrong-number sentence, unless the record's status is past New; C06 order number; C07 total; C08 payment line; B02 "متابعة الطلب / Track order"; B03 "العودة إلى المتجر / Back to store". Scrolled to the top. Nothing moves and nothing is announced except the screen itself (§7.6).

**There is no "retried" variant:** G-05 looks identical whether the response was `created` or `existing-identical`, and whether it arrived at M-01, at M-03, or is being re-rendered by a reload — in all of those cases only one order exists and the guest never learns how many requests were made.

**There is one already-existing variant, and it differs by two things only:** C09 is rendered, and C05 is suppressed when the returned status is past New (§5.2). No other element changes, no copy elsewhere on the screen changes, and the two entry paths (M-01 and M-03) produce exactly the same screen.

## 7. Field rules

Nothing is typed on G-05 and no field element exists (§4). The rules below govern the values it displays and its sizes.

### 7.1 Order number (C06)

- Shown exactly as the server returned it and as the record stores it: a string of Western digits 0–9, no prefix, no "#", no thousands separator, no reformatting. G-05 never derives, pads or shortens it.
- Laid out left-to-right in both languages.
- If the string is longer than 8 digits it still renders on one line at 20 px (8 digits at 20 px are about 100 px wide); G-05 does not wrap or truncate it.

### 7.2 Room number (C04)

- The record's room number string, byte for byte: **1–5** Western digits (G-04 §7.1), leading zeros kept. 48 px bold, letter-spacing 0.08 em, one line, never shrunk.
- G-05 does not re-validate it (M-01 §7.1 rule: G-04 is the single owner of the field rules).
- `{room}` inside C09 is this same string, rendered inline at 14 px with the same digits and the same leading zeros.

### 7.2.1 Status and the `already-existing` flag

- **Status:** one of the five values of locked decision 5, as saved in the record by M-01 §7.4 step 1. G-05 compares it against New and uses the result for one purpose only: C05 is rendered when the status is New and hidden when it is any later status. G-05 never prints it, never re-fetches it, and never writes it.
- **`already-existing` flag:** a single value handed over with the record by M-01 or M-03, set only for a response of kind `existing-different`. Present → C09 is rendered; absent → C09 is not rendered. It is not stored in the record and is therefore absent on every reload (§5.2).

### 7.3 Total and amount (C07, C08)

- Total: the record's total, two decimals, half-up rounding already applied by G-04; G-05 does not recompute it from the lines. Currency label per G-01 §7.2 (after the amount in Arabic, before it in English).
- Amount: the record's whole number, rendered with ".00". No amount → the second C08 variant (§5.4). Card → the first variant regardless of any amount value (G-04 clears the amount when Card is selected, §7.4; if a record ever carried both "card" and an amount, G-05 shows the Card variant and ignores the amount).

### 7.4 Language

- All fixed copy in the saved language. The record's numbers are language-independent. Switching language is not possible on G-05 (map §2.3 rule 6); the guest goes back to G-01 for the toggle, and G-06/G-07 render the order in whichever language is chosen later.

### 7.5 Sizes, touch targets, and layout

- Text sizes: C04 room number **48 px bold**; C01 title 22 px bold; C06 number 20 px bold; C07 16 px bold; C03 16 px; C05, C06 label, C08, C09 14 px; button labels 16 px bold. **Minimum text size on G-05 is 14 px** (G-01's floor is 10 px; this screen carries a safety message and has room to spare).
- The room number is at least 2 × the size of any other text on G-05, and no other text exceeds 22 px.
- Tap areas: B01 44 × 44 px; B02 and B03 358 × 56 px with a 12 px gap. Nothing else is tappable.
- Fit rule: at a 390 × 664 px viewport (the smallest common phone viewport with browser chrome), the whole content of the ordinary state including B03 is visible without scrolling — header 56 + top padding 32 + C02 64 + 16 + C01 26 + 24 + C03 20 + 8 + C04 88 + 12 + C05 40 (2 lines) + 24 + C06 24 + 8 + C07 20 + 4 + C08 20 + 32 + B02 56 + 12 + B03 56 + 16 = 658 px. **In the already-existing state the content is taller and the body scrolls**: C09 adds about 110 px (four lines at 14 px plus its 12 px padding and the 12 px gap), which C05's suppression offsets only when the status is past New. Scrolling is accepted here rather than shortening C09 or shrinking any element: the notice is the reason this state exists, and both buttons stay reachable by scrolling. On shorter viewports the body scrolls in every state; the header stays fixed.
- Contrast: C04 at least 7:1; all other text at least 4.5:1. Nothing is conveyed by color alone; the primary button is set apart by its dark fill. The screen must read correctly in grayscale.
- Browser zoom and text scaling are never disabled (G-01 §7.6). With enlarged text the body scrolls; the room number never shrinks below 48 px.

### 7.6 Accessibility and motion

- On open, a screen reader announces the title "تم إرسال طلبك / Order submitted", then C03, then the digits of C04 one by one, then C09 when it is shown, then C05 when it is shown, then C06, C07, C08, then the two buttons in order. Focus order: B01 → C01 → C03 → C04 → C09 (when shown) → C05 (when shown) → C06 → C07 → C08 → B02 → B03.
- The digits of C04 and C06 are read one digit at a time (M-01 §5.2 rule).
- No animation exists on G-05, so no reduced-motion variant is needed.

## 9. Decisions settled on this screen (not previously settled by CLAUDE.md, the map, or an earlier screen)

1. **The room number is the first data element, at 48 px bold in an 88 px box, at least 2 × the size of any other text**, with M-01's label repeated verbatim above it. This is the concrete form of the product manager's "prominently".
2. **A fixed one-line sentence under the room number tells the guest how to fix a wrong number** (cancel from tracking while the hotel has not accepted). Shown for every order whose record status is New; it is text, not a link; the action is the primary button. It is suppressed when the returned status is past New, because the cancellation it promises is no longer available (locked decision 6), and nothing replaces it.
3. **The order number is shown at 20 px, below the room number** — deliberately secondary.
4. **G-05 shows the total and the payment method (with the cash amount when given), and nothing else about the order**: no item count, no lines, no notes, no time, no status, no estimated delivery time.
5. **G-05 sends no request and has exactly one rendered state.** Loading, empty and error are unreachable by rule.
6. **The title lives in the body under the success mark; the header holds only the back arrow.**
7. **"Track order" replaces G-05 in the history**, so G-05 can never be reached by back from G-06.
8. **Reload renders from the device record; a missing record redirects to G-01 silently.** Forward navigation follows the same rule.
9. **"Back to store", the back arrow, and browser back are one action**: G-01 at the top, history reset to G-01 alone.
10. **Minimum text size 14 px on this screen**, above G-01's 10 px floor.
11. **The cash amount is rendered with two decimals** ("200.00 ر.س") to match every other amount in the interface.
12. **If a record ever carried "card" together with an amount, the Card variant is shown and the amount ignored** (G-04 prevents this; the rule exists so the technical team has no undefined case).
13. **G-05 has one already-existing variant, owned by this screen: C09.** It is rendered only when M-01 or M-03 hands over the `already-existing` flag (response kind `existing-different`), it is the only place in the product where that copy is written, and it adds no control and changes no other element.
14. **The `already-existing` flag is a hand-off and is not stored in the order record**, so a reload of G-05 shows the same order without C09; the status, which is stored, keeps governing C05 across a reload.
15. **G-05 reads the status from the record and never prints it**, using it for exactly one decision: whether C05's cancellation sentence is shown.
