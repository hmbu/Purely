Conventions reused verbatim from G-01, not re-decided here: Western digits 0–9 in both languages; currency label from store settings, after the amount in Arabic ("45.00 ر.س") and before it in English ("SAR 45.00"), two decimals always; the item-count rules of G-01 §7.3 and G-03 §7.3; every tappable element has a tap area of at least 44 × 44 px; browser zoom and text scaling are never disabled; no toast on this screen; the five status labels of G-01 §5.2.

**Why this screen carries two obligations beyond "show the status".**

1. **The room number, again, while cancelling is still possible** (`/spec/reviews/G-04.md` ruling R3). G-04 §5.3 decided the room number is not checked against a list of real rooms, so "305" typed as "350" passes every rule in the product. M-01 makes the guest read the number before sending; G-05 shows it immediately after sending; G-06 is the third and last sighting, and the only one that is still on screen while the order is in status **New**, which is the only status the guest may cancel (locked decision 6). That is why §5.4 puts the room number on its own line at 28 px bold and why §5.9 guarantees it is visible in the same view as "إلغاء الطلب / Cancel order".
2. **The stable client order key** (`/spec/reviews/G-04.md` ruling R5). The key identifies a *submission attempt* and never changes across edits, retries or reloads within one checkout session. If the server already holds an order for that key it returns **that** order instead of creating a second one — so the order the guest ends up with may carry values from before an edit. G-06 is where the guest discovers that, because it is the first screen that shows the order's **contents** as the server holds them next to the room number it is going to. The documented repair is cancel-while-New (§5.6), and nothing else in version 1 edits a submitted order.

## 1. ID and name

- **ID:** G-06
- **Name:** متابعة الطلب / Order tracking
- **Type:** Full guest screen with its own URL and history entry. The URL carries the order number (example: `…/order/1042`).
- **Language:** the language currently saved on the device (locked decision 7; map §2.3 rule 6). G-06 has no language toggle. RTL in Arabic, LTR in English; the room number, the order number, dates, times and amounts are laid out left-to-right in both languages (M-01 §1 rule).

## 2. Purpose

Show one order's live status as a timeline with its details, let the guest cancel it while it is still New, and let the guest order it again once it is finished.

## 3. Entry and exit points

Every entry renders from the **device order record** (M-01 §7.4 step 1) on the first frame, with the record's last known status, and then sends one status request (§5.5). Reading the record is synchronous, so there is no skeleton and no spinner (§6.1). G-06 **never fetches the catalog**, so it never leads to G-08 (the record carries product names in both languages and the prices that were charged).

### 3.3 Reload, backgrounding, and offline

- **Reload / direct URL:** §3.1 last two rows. Nothing is re-sent and nothing is lost; the record is on the device.
- **Tab hidden (backgrounded, device locked, another tab):** polling pauses (§5.5). Nothing else changes; the screen keeps what it last drew. On return to the foreground one status request is sent immediately and the cadence restarts.
- **Offline:** the whole screen renders from the record, so every value except the status freshness is correct. The status request fails, C05 appears (§5.5), and polling keeps trying every 20 seconds, so the screen heals by itself when the connection returns. B02 "Cancel order" is **not** hidden or disabled while offline (§5.6 rule 6). B03 "Reorder" still leads to G-03, which owns the offline case for the cart (G-03 §6.1 case (a), §6.3).

## 5. Content

### 5.0 What G-06 reads, what it writes, and what it never touches

G-06 renders **only** from the device order record written by M-01 §7.4 step 1, plus the status returned by its own status request. It reads: order number, order time, room number string, lines (product identifier, product name in both languages, quantity, unit price), notes, payment method, amount or none, total, last known status, and the two fields defined by this screen in §5.3 (the point of cancellation and who cancelled).

G-06 **writes** to the record only: the live status returned by a successful status request (map §2.3 rule 5), the point of cancellation, and the "cancelled by the guest on this device" flag when M-02 reports a successful cancellation (§5.6).

G-06 **never**: fetches the catalog; re-prices a line against the current catalog; recomputes the total from the lines; reads or writes the device cart (§5.7); deletes a record (G-07 §5.4 owns the only deletion); sends anything that identifies the guest (locked decision 4 — the status and cancellation requests carry the order number only).

### 5.1 Header (S01)

Layout, in visual order for Arabic (RTL): [B01 back chevron] … [C01 "متابعة الطلب"] … (nothing at the end edge). In English the chevron moves to the left edge and points left; the title stays centered. The end edge is deliberately empty: no language toggle (map §2.3 rule 6; the toggle lives on G-01 and G-08 only), no "My orders" button, no share, no print, no refresh control.

### 5.2 The order identity block (C03, C04)

- **C03 order number** — "رقم الطلب {order number} / Order number {order number}", the number at 20 px bold, printed exactly as stored and exactly as G-05 §5.3, G-07 §5.2 and G-01's banner print it. It is the one string the guest and the hotel share when they talk on the phone.
- **C04 current-status headline** — the canonical label of G-01 §5.2 at 22 px bold, on its own line. It exists in addition to the timeline because the timeline's answer is carried by markers and weight, and a guest with poor eyesight, or in a hurry at 2 AM, must be able to read the answer in one line without decoding a diagram. The label and the timeline can never disagree: both are rendered from the same single status value.

### 5.3 The timeline (S03, C07, C08) — and where Cancelled sits

The forward path of locked decision 5 has four steps, always in this order:

1. جديد / **New**
2. تم القبول وجارٍ التحضير / **Accepted & preparing**
3. في الطريق / **On the way**
4. تم التوصيل / **Delivered**

**Not cancelled.** All four rows are rendered, always, in this order, top to bottom. Each row is in exactly one of three conditions:

| Condition | Marker | Label |
|---|---|---|
| Reached (a step at or before the current status) — except the current one | Filled dark 24 px circle with a light check glyph | 16 px regular, dark |
| Current (the step equal to the current status) | Filled dark 24 px circle with a light filled dot | 16 px **bold**, dark |
| Not yet reached | Outlined gray 24 px circle, no glyph | 16 px regular, gray (contrast at least 4.5:1) |

The connector between two markers is a 2 px vertical line: dark between two reached markers, gray otherwise. Nothing is signalled by colour alone — glyph, weight and fill carry the meaning, and the screen reads correctly in grayscale.

**Cancelled — the decision.** Cancelled is not a fifth forward step and is never rendered as one. It is a **terminal row that replaces the steps that were never reached**:

- The rows for every step **up to and including the point of cancellation** are rendered as *reached*.
- Immediately beneath them, one row reads **ملغى / Cancelled**, with a filled dark marker carrying a light "×" glyph and a bold label. It is the current row.
- The forward steps after the point of cancellation are **not rendered at all** — no gray rows, no strikethrough, no "skipped" placeholder. A journey that ended is not drawn as a journey that is still missing steps.

Examples, with no other difference between them:

| Case | Rows rendered, top to bottom |
|---|---|
| Guest cancelled while New (locked decision 6) | جديد / New (reached) → ملغى / Cancelled (current) |
| Hotel cancelled after accepting (map §4 decision 15) | جديد / New (reached) → تم القبول وجارٍ التحضير / Accepted & preparing (reached) → ملغى / Cancelled (current) |
| Hotel cancelled while On the way | New → Accepted & preparing → On the way (all reached) → ملغى / Cancelled (current) |

**The point of cancellation** is taken, in this order of preference: (1) the last-reached status the server sends with the Cancelled status, when it sends one; (2) otherwise the last non-cancelled status the device record held before Cancelled was first seen. Preference (2) always yields a value, because every record starts at New (M-01 §7.4 step 1), so the row set is never undefined. Once written into the record the point of cancellation is never changed again.

**C08, the cancellation line**, sits directly under the Cancelled row and is the only place that says who cancelled and why:

| Case | Arabic | English |
|---|---|---|
| The record carries the "cancelled by the guest on this device" flag (§5.6) | ألغيتَ هذا الطلب | You cancelled this order |
| Cancelled without that flag, and the server sent no reason | ألغى الفندق هذا الطلب | The hotel cancelled this order |
| Cancelled without that flag, and the server sent a reason | ألغى الفندق هذا الطلب: {reason} | The hotel cancelled this order: {reason} |

- The reason is an optional free line written by staff (map §4 decision 15). It is shown **exactly as received, in whatever language staff wrote it**, never translated and never edited. Bound: 120 characters; anything longer is cut at 120 characters and closed with "…". An empty or whitespace-only reason is treated as no reason.
- A cancellation made on another device, or by staff, is indistinguishable to this device, so the second variant is what a guest sees for any cancellation this device did not perform. G-06 never guesses beyond that.
- No status other than Cancelled ever renders C08, and there is no reason line for Delivered.

**No times on the timeline.** No row shows a timestamp in version 1 — not "accepted at 14:12", not a delivery time on the Delivered row. Two reasons: the only time this product can state truthfully is the order time, which is already in C10 from the record; and a time observed by the phone (the moment this screen happened to see the status change) is not the time the thing happened, so printing it would be a claim the hotel never made. Per-status timestamps supplied by the server are a version-2 candidate; if the product manager wants them, they belong in `/spec/backlog.md`.

### 5.4 The room-number line (C06) — placement, size, and reason

- **Copy.** The ruled sentence of `/spec/reviews/G-04.md` R3, word for word, for the three active statuses: "سيُوصَّل طلبك إلى الغرفة {room}" / "Your order will be delivered to room {room}". For a finished order the same line changes tense only — "تم توصيل طلبك إلى الغرفة {room}" / "Your order was delivered to room {room}" for Delivered, and "كان هذا الطلب للغرفة {room}" / "This order was for room {room}" for Cancelled — because a future-tense promise on an order that is already delivered or cancelled is a false statement, and the safety requirement is about the statuses in which something can still be done. Size, placement and prominence are identical in all five.
- **Size.** The room number itself is **28 px bold**, letter-spacing 0.08 em, inline in the sentence whose words are 16 px. It is the largest text on G-06: the next largest is C04 at 22 px, then C03's number and C12's total at 20 px and 18 px. It is therefore never smaller than the order number, as R3 requires.
- **Placement.** Its own line, directly under the status headline and directly above the timeline — inside the first screenful, never in a collapsed section, an expandable "details" row, or a footer.
- **Fit guarantee.** §5.9 fixes the arithmetic that keeps C06, C16 and B02 visible together while the status is New, counting C05 and the safe-area inset.
- **Value.** The record's room number string byte for byte, leading zeros kept ("0305" stays "0305", G-04 §7.1), Western digits in both languages, laid out left-to-right, never wrapped and never shrunk. G-06 does not re-validate it (M-01 §7.1: G-04 is the single owner of the field rules).
- Contrast: the digits at least 7:1 against the background, like M-01 §5.2 and G-05 §5.2; every other text at least 4.5:1.

### 5.4a The repair line (C16) — why one line of copy replaces the button that disappears

**The reason it exists.** B02 "إلغاء الطلب / Cancel order" correctly disappears the moment staff accept the order (locked decision 6), and until now nothing replaced it. A guest who reads C06 and sees the wrong room number — or reads C11 and sees the wrong item — one minute after acceptance was told nothing at all, and a wrong delivery then proceeded silently with the guest watching it happen. That is an operational error caused by silence, not by the rule. C16 is the line that speaks: while the order is still New it names the repair the guest has, and once the hotel has accepted it says plainly that the repair is gone and names the one channel the hotel actually staffs.

**The two variants, and nothing between them.**

| Last known status | Variant | Arabic | English |
|---|---|---|---|
| New | **A** | هل هناك خطأ في هذا الطلب — رقم الغرفة أو المنتجات أو طريقة الدفع؟ ألغِ الطلب ما دام الفندق لم يقبله بعد، ثم أرسل طلبًا جديدًا. | Something wrong in this order — the room number, the items, or the payment method? Cancel it while the hotel has not accepted it yet, then place a new order. |
| Accepted & preparing | **B** | لم يعد بالإمكان إلغاء هذا الطلب من هاتفك بعد أن قبله الفندق. إذا كان فيه أي خطأ — رقم الغرفة أو المنتجات — اتصل بالاستقبال من هاتف الغرفة الآن. | This order can no longer be cancelled from your phone now that the hotel has accepted it. If anything in it is wrong — the room number or the items — call reception from your room phone now. |
| On the way | **B** | *(same as the row above, word for word)* | *(same as the row above, word for word)* |
| Delivered | — | *(C16 is not rendered)* | *(C16 is not rendered)* |
| Cancelled | — | *(C16 is not rendered)* | *(C16 is not rendered)* |

- **Variant A is one family with G-05-C05**, the repair sentence on the success screen: the same scope in the same order — any mistake (room number, items, payment method), cancel, the deadline (while the hotel has not accepted), order again. The only difference is that the guest reading C16 is already on the tracking page, so the sentence says "ألغِ الطلب / Cancel it" where G-05 says "from the tracking page". The two sentences are changed together or not at all.
- **Variant B states that the window is closed; it does not work around it.** It opens no request-cancellation path, offers no grace period and adds no control. Locked decision 6 is unchanged and is simply told to the guest in the one status family where they would otherwise learn it from a missing button.
- **Hidden on Delivered** (nothing can be repaired and nothing is coming), **hidden on Cancelled** (the order is already stopped and B03 "إعادة الطلب / Reorder" is the forward action), and **hidden in the error state** (§6.3, where C15's third line already names the room phone).
- **Suppressed while C02 is shown.** C02, as amended, ends with the same instruction for the specific case of a lost cancellation race; printing both would put the same sentence twice in one view. C16 returns if C02 is cleared by leaving G-06 and coming back while the status is still Accepted & preparing or On the way (§5.6 rule 5).
- **The variant swaps in place.** When a status response moves the order from New to Accepted & preparing, C16 swaps from variant A to variant B inside the same 100 ms repaint as C04, the timeline rows, C06's tense and the action bar (§5.5 rule 6) — no animation, no scroll change, and no announcement of its own beyond the existing status announcement (§7.5).
- **What C16 is not, by rule:** it is not a contact button ("Call reception", "Contact staff", "Report a problem"), not a `tel:` link, not a chat channel, not a message-to-staff field, not an edit-order path, and not a modal. It is a line of copy, exactly like C02's and C15's instructions, and §5.10's exclusion of contact controls stands unchanged. A button cannot dial a room phone, and a tappable number would invite a call from a mobile that may not reach the hotel's internal extension.

### 5.5 Status refresh — the decision, with numbers

G-01 §5.2 deliberately fetches once per load and never polls, because its banner is a pointer, not an answer. G-07 §5.5 does the same for its list. **G-06 is the one screen that polls**, because its entire purpose is the live status of one order (map §2.3 rule 5: "G-06 always fetches the live status from the server"). The rule, in full:

1. **On open:** one status request for this order number, sent as soon as the screen is drawn from the record.
2. **Then every 20 seconds**, measured from the moment the previous attempt ended (a response arrived, or its timeout elapsed), so two requests are never in flight at once. 20 seconds is chosen against the operation being tracked: a staff member accepting an order, walking a corridor and knocking takes minutes, so a status change reaches the guest within 20 seconds of it happening — fast enough that the guest does not sit watching a stale screen, and slow enough that one guest tracking one order costs three requests a minute.
3. **Request timeout: 10 seconds** — the same figure G-01 uses for the catalog and G-07 for its refresh. An attempt that has not answered in 10 seconds is a failure, and a response arriving after that is discarded for the screen (but a status it carries is still written into the record; it is the device's own data).
4. **Polling stops permanently** as soon as the status is **Delivered** or **Cancelled**. Both are final under locked decision 5, so there is nothing left to ask; the screen keeps what it shows until the guest leaves.
5. **Polling pauses** while the browser tab is hidden (backgrounded, device locked, another tab), and while **M-02 is open** (so the guest is never shown a status change under a modal that is asking about the old one). On return to the foreground, and when M-02 closes, one request is sent immediately and the 20-second cadence restarts from that attempt.
6. **On success:** the returned status is written into the record (map §2.3 rule 5) and the screen updates in place within 100 ms — C04 headline, the timeline rows, C06's tense, **C16's variant (§5.4a)**, the action bar's buttons (§5.8), and C05 hidden. No sound, no highlight, no toast, no scroll change.
7. **On failure** (no connection, server error, unreadable response, or 10-second timeout): the screen keeps the last known status and shows **C05** "تعذّر تحديث الحالة — هذه آخر حالة معروفة / Could not update the status — this is the last known status". C05 disappears on the first successful attempt. G-06 shows it where G-01 and G-07 stay silent because those two screens are showing a pointer to this one, whereas here the guest is looking at the status itself and must know it is not confirmed.
8. **On "order not found"** — the server answers that it holds no order with this number: the error state (§6.3) replaces the success state, at whatever moment the answer arrives. The record is **not** deleted (G-07 §5.4 owns deletion).
9. **No pull-to-refresh, no "refresh" button, no "last updated" time, no "updating…" indicator.** The 20-second poll makes a manual refresh a second way to do what the screen already does, a timestamp is already deferred for the banner (backlog G-01-L4), and a spinner on a screen that repaints every 20 seconds is movement without information.

### 5.6 Cancelling — what G-06 does and what M-02 does

Locked decision 6: the guest may cancel only before staff accept. G-06 enforces it by **rendering B02 only while the last known status is New**, and by handing the act itself to M-02 (map §1.2). G-06 never sends a cancellation request of its own.

1. **What G-06 hands M-02** on a tap of B02: (a) the order number; (b) the status G-06 currently shows, which is always New. Nothing else. M-02's contents, copy and internal error handling belong to the M-02 file.
2. **What G-06 expects back** — exactly one of three outcomes, with no fourth:

| Outcome from M-02 | What G-06 does |
|---|---|
| **Cancelled** — the server accepted the cancellation | Writes into the record: status **Cancelled**, the point of cancellation (**New**, §5.3), and the "cancelled by the guest on this device" flag. Re-renders within 100 ms: C04 reads "ملغى / Cancelled", the timeline shows New → Cancelled, C08 reads "ألغيتَ هذا الطلب / You cancelled this order", C06 switches to its Cancelled tense, and the action bar swaps B02 for B03 (§5.8). Polling stops (§5.5 rule 4) |
| **Already accepted** — staff accepted before the cancellation arrived (map §4 decision 11) | Writes the real status M-02 returned into the record. Re-renders the timeline, headline and action bar for that status — so B02 disappears, because the order is no longer New — and shows **C02**, the "already accepted" banner, whose second line reads "إذا كان في الطلب أي خطأ، اتصل بالاستقبال من هاتف الغرفة الآن. / If anything in the order is wrong, call reception from your room phone now." **C16 is suppressed while C02 is shown** (§5.4a), because C02's second line is that same instruction. **No modal, no second dialog, no error screen:** the guest is shown what is true and two sentences saying why the tap did not do what they asked and what to do about it |
| **Failed** — the request could not be sent or was not answered | **Nothing at all.** M-02 owns that case and stays open with its own error text and its own two buttons (map §2.2, M-02 row). G-06 is unchanged beneath it, the record is unchanged, and no banner is shown |

3. **"Keep order" or a backdrop tap on M-02**: M-02 closes, G-06 is unchanged, polling resumes with one immediate request (§5.5 rule 5).
4. **The race is only ever resolved by the server.** G-06 does not pre-check the status on the B02 tap and does not disable B02 while a poll is in flight. A guest who taps B02 half a second before staff tap "accept" gets the *already accepted* outcome, which is the designed answer, not an error.
5. **C02 lifetime:** the banner is held in the screen's memory only. It stays visible for the rest of this visit to G-06 (it does not time out and has no close button), and it is gone after leaving the screen or reloading, because by then the status on screen is already the truth and the first sentence would be explaining something the guest has stopped asking. While it is on screen C16 is suppressed; when the guest leaves and returns while the status is still Accepted & preparing or On the way, C02 is gone and **C16 variant B takes over the instruction**, so the guest is never left without it (§5.4a).
6. **B02 is never hidden or disabled by a failed poll or by being offline.** The device cannot know whether the hotel has accepted; hiding the only repair path because a request failed would strand exactly the guest who needs it. The tap opens M-02, and M-02 reports what happens.
7. **There is no "un-cancel" and no second chance:** once the status is Cancelled, B02 is gone for good and B03 "Reorder" takes its place (§5.8).

### 5.7 Reorder — the handoff contract to G-03

Map §4 decisions 7 and 8 put Reorder on G-06 only, and the G-03 review (`/spec/reviews/G-03.md` §6.1 item h) makes the following binding on this file: **G-06 hands the previous order's lines to G-03 and does not touch the device cart itself**, so that the merge, the single availability check and the max-10 cap live in one place.

On a tap of B03, G-06:

1. Reads the record's lines and builds the handoff: an ordered list of **(product identifier, quantity)** pairs, in the record's stored line order. Nothing else is handed over — no names, no prices, no totals, no notes, no room number, no order number.
2. Opens G-03, pushed above G-06, and passes that list.
3. Ignores further taps on B03 until G-03 is on screen, so a double-tap hands off once.

G-06 explicitly does **not**: read the device cart; write the device cart; check availability; read or write the session catalog copy or its out-of-stock marks; apply the maximum of 10 per line; show a toast; show a preview, a "replace cart?" question, or any confirmation; change anything if the guest comes back. All of that is G-03 §5.7, and G-03 owns the outcome, including the case where every product is skipped and the cart ends up empty. A line whose product no longer exists in the catalog is still handed over; G-03 skips it and counts it in its toast.

Returning from G-03 by its back arrow lands on G-06 unchanged (G-03 §3.2, "the opener"): the order shown here is finished, so nothing about it can have changed.

### 5.8 The action bar (S05) — what is offered in each status

S05 is fixed to the bottom of the viewport so that B02 is reachable without scrolling past the whole order (§5.9). Its contents are decided by the last known status and by nothing else:

| Last known status | Buttons, top to bottom | Bar height |
|---|---|---|
| New | B02 "إلغاء الطلب / Cancel order" (outlined), B04 "العودة إلى المتجر / Back to store" (outlined) | 148 px (12 + 56 + 12 + 56 + 12) |
| Accepted & preparing | B04 only | 80 px (12 + 56 + 12) |
| On the way | B04 only | 80 px |
| Delivered | B03 "إعادة الطلب / Reorder" (dark filled), B04 (outlined) | 148 px |
| Cancelled | B03 (dark filled), B04 (outlined) | 148 px |
| Error state (§6.3) | B04 only | 80 px |

- The bar's height changes when the status changes; S02's bottom padding changes with it in the same frame, so no content is ever left under the bar.
- **B02 is deliberately not the primary style.** Cancelling is a repair, not the screen's goal, so it is an outlined button of the same size as B04; neither is dark filled while the status is New, and the guest is not pushed toward either. B03 *is* dark filled, because on a finished order ordering again is the only forward action on the screen.
- Nothing in the bar is distinguished by colour alone: the two shapes (filled, outlined) plus the labels carry it, and the bar reads correctly in grayscale.
- Middle statuses (Accepted & preparing, On the way) offer exactly one action. There is no "contact staff", no "call reception" button, no "edit order", no "add to this order", no "report a problem", no "rate the order" (§5.10).

### 5.9 The safety guarantee: the room number and "Cancel order" in one view

`/spec/reviews/G-04.md` R3 requires that while the status is New, the room-number line is visible **in the same view as** the cancel control. The layout fixes this by arithmetic rather than by hope. The proof below counts **every element that can be on screen in status New** — including C05, which §4 places between C04 and C06 and which appears exactly in the weak-connection case, and C16, the repair line — and it counts the safe-area inset that §4's S05 row requires.

**The measurement basis, stated once.** Viewport 390 × 664 px (the smallest common phone viewport with browser chrome). §4's S05 row requires "12 px padding plus the device's safe-area inset", and **the inset is counted explicitly at 34 px**, so the New-status action bar occupies **148 + 34 = 182 px**. Worst cases: **C05 shown at 2 lines**, **C06 at 2 lines**, **C16 variant A at 3 lines**. C02 is not counted here because it cannot appear while the status is New (§5.6). The gaps are the authoritative ones listed in §4.

| Region | Height |
|---|---|
| S01 header | 56 |
| S02 top padding | 24 |
| C03 order-number line | 24 |
| gap | 8 |
| C04 status headline | 28 |
| gap | 8 |
| **C05 stale-status notice (2 lines, worst case)** | **40** |
| gap | 8 |
| C06 room line (2 lines, the worst case, with a 28 px number) | 68 |
| gap | 8 |
| **C16 repair line, variant A (3 lines, worst case)** | **60** |

**The guarantee, and it now holds on its own terms:** at 390 × 664 px with a 34 px safe-area inset, default text size, C05 shown and C16 at 3 lines, **C03, C04, C05, C06, C16 and B02 "إلغاء الطلب / Cancel order" are all fully visible on the first painted frame without scrolling**, and the 150 px of free space still shows the first two timeline rows (56 px each).

**What must give, ranked, decided now so it is never decided ad hoc.** If a future change breaks the inequality, the sacrifice order is: **(1) the timeline rows scroll out of the first screenful** — they are information, not a repair; then **(2) C05 may wrap below the fold** — a notice about status freshness is the least load-bearing line on the screen. **Never C06, never C16, never B02:** the room number, the repair sentence and the cancel control share the first screenful while the status is New, or the requirement of `/spec/reviews/G-04.md` R3 is not met. **No element may be shrunk, collapsed, moved into an expandable region, or deleted to make the sum work**, and C06 never renders below 28 px.

**The past-New case, proved in one line.** With C02 shown (≈ 80 px including its padding and the 16 px below it), C16 suppressed (§5.4a) and the bar at 80 + 34 = **114 px**, the bottom of C06 sits at **344 px** against a bar top of **550 px**: C02, C04 and C06 are all on the first screenful, so the guest who has just lost the cancellation race reads the banner, the real status and the room number without scrolling.

If the guest enlarges the browser's text, the body scrolls while S05 stays fixed, so B02 never leaves the viewport; C06 may then need a scroll, and that is accepted — the requirement is that the guest cannot reach "Cancel order" without having passed the room number, and the room number is above it in the scroll order.

### 5.10 What is deliberately not on this screen

Each item was considered and left out, because G-06 has one purpose (§2) and every extra control is another thing to specify, test and explain.

- **No editing of a submitted order**: no "add items to this order", no quantity change, no note change, no room-number change, no "change payment method". Version 1's answer to "I want to change my order" is cancel-while-New then order again (map §3), and C06, C16 variant A and B02 are that answer made visible.
- **No cancel outside status New** (locked decision 6). There is no "request cancellation" for a later status, no grace period, and no message inviting one: C16 variant B states that the window is closed and points at the room phone, which invites nothing from this interface.
- **No "contact staff", chat, call button, or free-text message to the hotel.** This product points the guest at reception in exactly **four places** — C02, C15, C16 variant B, and G-07's empty state — and all four are written as instructions, never as tappable dial links; the guest is in a hotel room with a room phone, which is the channel the hotel actually staffs. **C16 is a line of copy, not a control: it is not tappable, carries no `tel:` link, and opens nothing.**
- **No delivery time, no countdown, no "arrives in about N minutes", no per-status timestamps** (§5.3). The hotel has not committed to a time anywhere in version 1.
- **No rating, feedback, tip, or "order again?" prompt after Delivered** beyond B03.
- **No map, no courier name, no staff photo.**
- **No share, print, receipt download, or "email me this order".**
- **No language toggle** (map §2.3 rule 6), no "My orders" button, no active-order banner (G-01 only), no floating cart bar, no hotel name.
- **No toast** (G-01 convention). The only modal that opens from G-06 is M-02.
- **No manual refresh and no pull-to-refresh** (§5.5 rule 9).
- **No delete / hide / archive control for this order** (G-07 §5.4 owns deletion, and it is only the 20-record trim).

### 5.11 The stable client order key, and why this screen must be unmistakable

`/spec/reviews/G-04.md` R5 settled the contract: the client order key is generated once per checkout session, is **never** replaced because a value changed, and the server returns the order it already holds for that key instead of creating a second one. Two consequences land on G-06, and the technical team must build for both:

1. **The order the guest is looking at may not be the order they last typed.** If a response was lost and the guest edited the room number, the notes, the payment method or the cart before retrying, the server answers with the order it already created — the one carrying the *earlier* values. M-01 applies that answer as a normal success, G-05 shows it, and **G-06 is where the guest has the time to notice**, because it is the first screen that shows the room number and the order's contents together, at rest, with a repair still available. That is why C06 is 28 px, why C11 lists every line with its quantity, and why C12 and C13 print the total and the payment method the server actually holds.
2. **Cancel-while-New is the documented repair path, and the only one.** A guest who reads a room number or a line that is not what they meant taps B02, M-02 cancels the order, and the guest places a fresh order — a fresh checkout session with a new key (G-04 §7.7 as amended by R5). There is no "fix this order" control, and version 1 does not offer one. If the status has already moved past New, the repair is the room phone, which is what **C16 variant B** says on every visit in the statuses Accepted & preparing and On the way, and what C02's second line says in the specific case of a lost cancellation race (§5.4a).

G-06 therefore prints only values that came back from the server through the saved record, never a local guess, and never a value the guest typed but the server did not accept.

## 6. States

### 6.1 Loading

**Not rendered, by rule** — the same rule as G-07 §6.1. The record is read from the device synchronously and drawn on the first frame of every entry, including a reload and a direct URL open; the status request runs after the first paint and is invisible while it runs (the screen shows the last known status until an answer changes it). There is no skeleton, no spinner, no placeholder, and no "loading status…" text anywhere on G-06. If a build ever needs more than 100 ms to read the record, it draws the header first and then the body, never a blank screen with a spinner.

### 6.2 Empty

**Unreachable.** A record always carries an order number, an order time, a room number, at least one line, a payment method, a total and a status (M-01 §7.4 step 1 guarantees all of them before G-05 is drawn), so there is no "order with nothing in it" to render. The only "nothing to show" case is *no record at all*, and that is the error state (§6.3), not an empty state. A record that is missing any of those fields is treated as unreadable and also renders the error state — the same treatment G-07 §6.3 case 2 gives it, with the difference that G-07 can skip a bad row while G-06 has nothing else to draw.

### 6.3 Error

G-06 has exactly **one** rendered error state: **"لم نعثر على هذا الطلب / We could not find this order"**. It is reached by exactly three triggers and no others:

1. The device holds **no record** for the order number in the URL (a cleared browser, another device, another browser, a typed or shared URL, a record the G-07 trim removed).
2. The device's record for that number is **unreadable** (§6.2).
3. A status request answers that the server **holds no order with this number** (§5.5 rule 8), at any moment, including in the middle of a visit.

On screen: S01 header with B01 and C01; C15 centered in the area under the header, with its icon and three lines; S05 containing B04 "العودة إلى المتجر / Back to store" only. S02's body content (C02–C14 and C16) and S03/S04 are not rendered — C15's third line already names the room phone, so C16 would repeat it. No status request is sent while the error state is shown (triggers 1 and 2), and polling stops when trigger 3 produced it.

Copy, exactly:

- Line 1 (18 px, bold): "لم نعثر على هذا الطلب" / "We could not find this order"
- Line 2 (14 px): "قد يكون أُرسل من جهاز آخر، أو لم يعد موجودًا لدى الفندق" / "It may have been sent from another device, or it is no longer in the hotel's system"
- Line 3 (14 px): "للسؤال عنه، اتصل بالاستقبال من هاتف الغرفة" / "To ask about it, call reception from your room phone"

**C15's third line is deliberately different from C02's second line and from C16 variant B, and stays different.** C02 and C16 say "إذا كان في الطلب أي خطأ… اتصل بالاستقبال… الآن / if anything in the order is wrong… call reception… now", because there the guest is looking at a real order that may be wrong and a delivery may be in motion. In the error state there is no order on this device to be wrong about, so asking is genuinely all the guest can do, and promising more would be a claim this screen cannot support. The three lines are not to be harmonised.

**Why a state and not a silent redirect.** G-05 §3.3 redirects to G-01 without a message when its record is missing, because G-05's job — telling the guest the order was sent — is already done by the time anyone can reload it. G-06 is the screen a guest opens to *ask a question*; answering "where is my order?" by quietly showing the shop leaves the question unanswered and the guest tapping again. The three lines answer it and point at the one channel that always works.

**The record is never deleted by this state.** G-07's 20-record trim is the only deletion in version 1 (G-07 §5.4), so an order the server does not know about still has its row on G-07 with its last known status (G-07 §5.5), and tapping that row lands here again with the same three lines.

**Failures that are not this state.** A failed or timed-out status request is **not** an error state: the screen stays in its success state with the last known status and shows the one-line notice C05 (§5.5 rule 7). A failed cancellation is not an error state either: M-02 keeps it (§5.6 outcome *failed*). There is no other error text anywhere on G-06, no error modal, and no toast.

Nothing is typed on G-06, so there are no field error messages.

### 6.4 Success

The device holds a readable record and the server has not said the order is unknown. This is the state for **all five statuses**; they differ only in C04's label, the timeline rows (§5.3), C06's tense, **C16's variant or absence (§5.4a)**, C08's presence, and the action bar's buttons (§5.8).

On screen, top to bottom: S01 [B01, C01]; C02 only after an *already accepted* outcome; C03 order number; C04 status headline; C05 only while the most recent status attempt failed; C06 room line; C16 repair line — variant A in New, variant B in Accepted & preparing and On the way, absent in Delivered, in Cancelled and while C02 is shown; S03 timeline with its rows and, when Cancelled, C08; S04 details with C09, C10, one C11 per line, C12, C13, and C14 when notes exist; S05 with the buttons for the current status. Scrolled to the top on every entry.

Update feedback: when a status response changes the status, every affected element repaints within 100 ms with no animation, no scroll change, no highlight and no toast; the guest's scroll position is kept exactly.

## 7. Field rules

Nothing is typed on this screen and no field element exists (§4). The rules below govern the values G-06 displays, the requests it makes, and the taps it accepts.

### 7.1 Values shown, and their source

| Value | Source | Rule |
|---|---|---|
| Order number (C03) | Record, server order number | Printed exactly as stored: Western digits, no "#", no thousands separator, no padding, no truncation; identical to G-05 §7.1 and G-07 §7.1 |
| Status (C04, timeline, action bar) | The live status when a request has succeeded during this visit; otherwise the record's last known status | Always one of the five canonical values of G-01 §5.2. A status outside those five makes the record unreadable (§6.2) |
| Room number (C06) | Record, room number string | Byte for byte, leading zeros kept, 1–5 Western digits (G-04 §7.1 as amended by ruling R1), 28 px bold, one line, never shrunk, never re-validated |
| Order time (C10) | Record, order time | The format of G-07 §5.6 and §7.2: "اليوم HH:MM / Today HH:MM" on the device's current local date, otherwise "DD/MM/YYYY HH:MM"; 24-hour clock, numeric date, Western digits, device time zone, laid out left-to-right in both languages |
| Product name (C11) | Record, the stored name in the current language | Maximum 2 lines, then an ellipsis. If the English name is missing, the Arabic name is shown in the English interface too (G-01 §5.4 rule). Names are never re-read from the catalog, so an order still renders after a product leaves the catalog |
| Quantity (C11) | Record, line quantity | The quantity that was ordered, 1–10; never editable here |
| Line total (C11) | Record, quantity × stored unit price | Two decimals, half up, currency per G-01 §7.2. **Never re-priced** against the current catalog |
| Items (C12 row 1) | Record | The sum of the stored line quantities, as a plain number, exactly as G-03 §7.3 prints it |
| Total (C12 row 2) | Record, total | The stored total, printed as stored, two decimals. **Never recomputed** from the lines: it is the amount the guest agreed to pay and staff collect |
| Payment and amount (C13) | Record, payment method and amount | The three variants of G-05 §5.4 word for word; the cash amount rendered with two decimals; a record carrying "card" together with an amount shows the Card variant and ignores the amount (G-05 §9 item 12) |
| Notes (C14) | Record, notes | Shown in full, exactly as sent, maximum 200 characters by G-04's own bound; wrapped over as many lines as needed, never truncated, never translated. Hidden when empty |
| Repair line (C16) | Fixed interface copy, chosen by the last known status | Variant A in New, variant B in Accepted & preparing and On the way, not rendered in Delivered, in Cancelled, in the error state or while C02 is shown (§5.4a). It carries no value from the record and no link |
| Cancellation reason (C08) | The status response, optional | Shown exactly as received in whatever language staff wrote it; cut at 120 characters with "…"; empty or whitespace-only is treated as absent (§5.3) |

### 7.2 Status request bounds

- One request on open; then one every **20 seconds**, measured from the end of the previous attempt; never two in flight at once.
- Per-attempt timeout **10 seconds**; a late response is discarded for the screen but its status is still written to the record.
- Polling **stops** at Delivered or Cancelled, and in the error state. Polling **pauses** while the tab is hidden and while M-02 is open, and resumes with one immediate attempt.
- The request carries the order number only — nothing that identifies the guest (locked decision 4).
- A failed attempt shows C05 and nothing else: no retry button, no counter, no timestamp, no escalation after N failures.

### 7.3 Tap handling

- B01, B02, B03 and B04 each respond to a single tap. After a tap on B02, B03 or B04, that button ignores further taps until the modal or the next screen is on display, so a double-tap acts once (the 300 ms convention of G-01 §7.1 applies as the floor).
- Nothing else on G-06 is tappable: not the timeline rows, not the order lines, not the banners, not the room number, **not C16** (which carries no link of any kind). A tap on any of them does nothing at all — no navigation, no selection, no visual reaction.
- There is no long-press, no swipe gesture, and no pull-to-refresh anywhere on the screen.

### 7.4 Language

- Every fixed string renders in the language saved on the device at render time (locked decision 7). Switching the language is done on G-01 and G-08 only; returning to G-06 afterwards re-renders every label, the status labels, the "Today" word, the count wording and the currency position in the new language.
- Values that are not interface copy — the room number, the order number, times, amounts, the notes, and the staff cancellation reason — are never translated and never reformatted by a language switch.

### 7.5 Sizes, touch targets, text, and accessibility

- Text sizes: C06 room number **28 px bold**; C04 22 px bold; C03 number 20 px bold; C12 row 2 18 px bold; C01 18 px bold; C07 step labels 16 px; C09 16 px bold; everything else 14 px. **Minimum text size on G-06 is 14 px** (as on G-05 and G-07). Nothing on this screen is smaller.
- The room number is the largest text on the screen and is never smaller than the order number (`/spec/reviews/G-04.md` R3).
- Tap areas: B01 44 × 44 px; B02, B03 and B04 each the inner width × 56 px, with a 12 px gap between two buttons in S05.
- Contrast: the room number at least 7:1 against its background; every other text at least 4.5:1, including gray future-step labels and C05. Nothing is signalled by colour alone — timeline state is carried by glyph, fill and weight; button rank by fill versus outline. The screen reads correctly in grayscale.
- Browser zoom and text scaling are never disabled (G-01 §7.6). With enlarged text the body scrolls under the fixed header and the fixed action bar, rows grow and lines wrap; nothing is truncated or hidden, and the room number never renders below 28 px.
- Screen reader: on arrival the title "متابعة الطلب / Order tracking" is announced, then C03, then C04, then C05 when present, then C06 with the room digits read **one at a time** ("zero three zero five", M-01 §5.2 convention), then C16 when it is shown, then the timeline as a list whose items are announced as "{step label} — {تم / Done}", "{step label} — {الآن / Now}", or "{step label} — {لم يبدأ بعد / Not yet}", then C08 when present, then the details in order, then the buttons. When a status change repaints the screen, the new status is announced once as "{order number}: {status label}" (the same announcement G-07 §7.5 makes); C16's swap from variant A to variant B is **not** announced separately — the status announcement is the event, and the guest who moves focus into the body reads the new line there. When C02 appears, its two lines are announced once. C05 appearing is announced once; it is not repeated on every failed poll.
- Motion: G-06 has no animation at all — no progress animation on the timeline, no fade on a status change, no spinner. There is therefore no reduced-motion variant.

## 9. Decisions settled on this screen (not previously settled by CLAUDE.md, the map, or an earlier screen)

1. **G-06 polls; it is the only screen that does.** One status request on open, then one every 20 seconds measured from the end of the previous attempt, with a 10-second per-attempt timeout, paused while the tab is hidden or M-02 is open, and stopped for good at Delivered or Cancelled (§5.5). G-01 §5.2 and G-07 §5.5 deliberately keep their single fetch; this screen is where the live value belongs.
2. **A failed status attempt is announced on this screen, quietly.** C05 "تعذّر تحديث الحالة — هذه آخر حالة معروفة / Could not update the status — this is the last known status" is shown whenever the most recent attempt failed, and disappears on the first success — unlike G-01 and G-07, which stay silent, because those screens point at this one while this one *is* the answer.
3. **No refresh control, no pull-to-refresh, no "last updated" time** (§5.5 rule 9).
4. **Cancelled is a terminal row that replaces the unreached steps**, placed after the steps actually reached; the later steps are not drawn at all (§5.3). The point of cancellation comes from the server when it sends one, otherwise from the last non-cancelled status the record held — which is always at least New, so the row set is never undefined.
5. **No timestamps on the timeline, and a Delivered order shows no delivery time** (§5.3). The order time in C10 is the only time on the screen; per-status times are a version-2 candidate for `/spec/backlog.md`.
6. **The order details block holds exactly seven things**: order time, one row per line as "{qty} × {name}" with its line total, Items, Total, the payment line, and the notes when they exist (§4, §7.1). No images, no unit prices, no product links, no room number repeated inside it (C06 owns the room number), no status repeated inside it.
7. **The room-number line is C06: its own line, the number inline at 28 px bold, directly under the status headline and above the timeline**, in every status, and never smaller than the order number — with §5.9's arithmetic guaranteeing that it and "Cancel order" share the first screenful while the status is New.
8. **The room line changes tense with the status** (will be delivered / was delivered / was for), keeping the ruled copy verbatim in the three statuses where something can still be done. The sizes and the placement never change.
9. **G-06 hands M-02 two values — the order number and the current status — and expects exactly three outcomes back**: cancelled, already accepted, failed. G-06 owns none of M-02's copy and performs no cancellation request itself (§5.6).
10. **The "already accepted" answer is a banner (C02) with two ruled lines, no close button, no modal, and no persistence across a reload** (§5.6 rule 5).
11. **"Cancelled by the hotel" and "cancelled by you" are told apart by a flag this screen writes when M-02 succeeds on this device**; any other Cancelled status is attributed to the hotel, with the staff reason appended when one exists and cut at 120 characters (§5.3).
12. **B02 stays visible and tappable while offline or while a poll is failing** (§5.6 rule 6): the device cannot know the hotel's answer, and hiding the repair path would strand the guest who needs it.
13. **The action bar is fixed to the bottom and its contents are decided by the status alone**; B02 and B04 are both outlined (cancelling is never the primary action), B03 is the only dark-filled button on the screen (§5.8).
14. **Reorder hands (product identifier, quantity) pairs to G-03 and nothing else, and G-06 never touches the device cart, availability, the max-10 cap or the toast** (§5.7) — the binding constraint from `/spec/reviews/G-03.md` §6.1 item h.
15. **One error state, three triggers, and it is not a redirect** (§6.3): no record, an unreadable record, or a server "no such order". G-05 redirects silently in the equivalent case because its job is finished; G-06 must answer a question the guest is still asking.
16. **G-06 has no loading state and no empty state, by rule** (§6.1, §6.2), and it never fetches the catalog, so it never leads to G-08.
17. **Nothing on the screen is tappable except the four buttons** (§7.3); the timeline and the order lines are information, not navigation, and there is no path from G-06 to G-02.
18. **Minimum text size 14 px; the room number at 28 px is the largest text on the screen**; no animation exists anywhere on G-06 (§7.5).
19. **Stored values are printed, never recalculated**: the total, the line totals, the item count and the names all come from the record, so an order renders correctly after a price change, a catalog change, or a language switch (§7.1).
20. **This screen is the discovery point for the stable-key contract** (§5.11): it prints what the server holds, and cancel-while-New is the only repair version 1 offers — after that, the room phone.
21. **C16, the repair line, is one persistent line of copy with exactly two variants and no control** (§5.4a). Variant A is shown in status New and names any mistake, the cancellation, its deadline and ordering again — one family with G-05-C05. Variant B is shown in Accepted & preparing and On the way and states that cancelling from the phone is no longer possible, pointing at reception on the room phone. C16 is not rendered in Delivered, in Cancelled or in the error state. It adds no button, no `tel:` link, no chat, no field, no modal and no post-acceptance cancellation path: locked decision 6 is stated by variant B, never widened.
22. **C16 is suppressed while C02 is shown**, because C02's second line carries the same instruction, and it returns when C02 is gone and the status is still Accepted & preparing or On the way (§5.4a, §5.6 rule 5).
23. **The first-screenful guarantee is proved with every element that can be on screen in status New — C05, C06 and C16 — and with the safe-area inset counted at 34 px** (§5.9). The ranked sacrifice order, if a future change breaks the inequality, is the timeline rows first, then C05's wrap; never C06, never C16, never B02, and nothing is shrunk, collapsed, moved into an expandable region or deleted to make the sum work.
