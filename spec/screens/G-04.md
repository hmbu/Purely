# G-04 — Checkout (إتمام الطلب)

Author: Thinker (Agent 1)
Status: **Draft** (status is changed only by the orchestrator in `/spec/screens-map.md`)
Governing documents: `/CLAUDE.md` locked decisions 1–7; `/spec/screens-map.md` §4 decisions 1–16; conventions set by `/spec/screens/G-01.md` (Western digits 0–9 in both languages; currency after the amount in Arabic "45.00 ر.س" and before it in English "SAR 45.00", two decimals always; tap area of at least 44 × 44 px for every tappable element even when the visible shape is smaller; 14 px minimum body copy).

This is the highest-stakes screen in the product: what the guest types here is what staff carry to a door. Every rule below is written so that a wrong room number, a wrong payment method, or a wrong "amount you will pay with" is caught on the device before it reaches staff.

---

## 1. ID and name

- **ID:** G-04
- **Name:** إتمام الطلب / Checkout
- **Type:** Full guest screen. Reached only from G-03 Cart (and re-shown under the three modals that open on top of it: M-01, M-03, M-04).
- **Language:** the language currently saved on the device (locked decision 7; map §4 decision 12). G-04 has no language toggle; the toggle lives on G-01 and G-08 only.

---

## 2. Purpose

Collect the three things staff need to deliver the cart to the right door — room number, payment method (with the optional cash amount), and optional notes — and hand them to M-01 for the mandatory room-number confirmation.

---

G-03 then shows its empty state or its out-of-stock-marked lines. This is why G-04 has no empty state of its own (§6.2).

### 3.2 Exit (where each action leads)

| Action on G-04 | Destination |
|---|---|
| Tap the back arrow (B01) or the browser back gesture | G-03 Cart, with the checkout draft kept (§7.7) |
| Tap "تعديل السلة / Edit cart" (B02) | G-03 Cart, with the checkout draft kept — identical to B01 |
| Tap "بطاقة / Card" (B03) | Stays on G-04; Card selected, Cash unselected; F03 amount field, C11 and C12 hidden; any amount value and amount error cleared |
| Tap "نقدًا / Cash" (B04) | Stays on G-04; Cash selected, Card unselected; C11, F03 (and C12 when it has an error) shown directly under the Cash row; F03 is not focused automatically |
| Tap "إرسال الطلب / Submit order" (B05) with any invalid field | Stays on G-04; keyboard closes; every error is shown inline; the screen scrolls to the first invalid element in the order F01 → payment (B03/B04) → F03 (§7.6) |
| Tap "إرسال الطلب / Submit order" (B05) with every field valid | M-01 opens on top of G-04 with the handoff in §7.8. **The order is never sent from G-04** (locked decision 2); only M-01's "Confirm and send" sends it |
| Guard fails on render (§3.1) | G-03 replaces G-04 |

G-04 never leads to G-05 directly; G-05 is reached only through M-01 (or M-03 "Retry") succeeding, as the map's flow shows. After that success, G-04 is dropped from the history (map §2.3 rule 3).

## 5. Content

### 5.1 Header (S01)

Layout in visual order for Arabic (RTL): [B01 back arrow] … [C01 "إتمام الطلب"] … (empty end edge). In English the arrow flips to the left edge and points left; the title stays centered. There is no language toggle and no "My orders" button on G-04: the checkout keeps one purpose, and both controls are one back-tap away on G-01.

### 5.2 Order summary (S02)

A single bordered box at the top of the form, so the guest sees what will arrive before typing anything. The only thing that can sit above it is C13, the "your order has not been sent yet" notice, which appears on the return from M-04 and contains one line of text and the "!" circle icon — no button, no close control, no second line (§4, §7.7).

- C02 title "ملخص الطلب / Order summary".
- One C03 line per cart line, in the order the lines appear on G-03 (the order they were added to the cart; G-04 never re-sorts). Each line: start side "{qty} × {product name}" (14 px; the name in the current language, one line, ellipsis "…" when too long; if the English name is missing the Arabic name is shown in the English interface too, as on G-01); end side the line total = qty × unit price as currently held in the session catalog copy, two decimals, currency per convention. No image, no unit price, no stepper, no remove control: every change to quantities happens on G-03, reached by B01 or B02.
- A 1 px gray rule, then C04 "الإجمالي / Total" with the total (§5.5).
- B02 "تعديل السلة / Edit cart" as the last row, at the end side.
- **All lines are shown**, however many there are; there is no "show more" expander. The screen scrolls.
- The summary is **rebuilt from the device cart every time G-04 is rendered** (arrival, reload, return from M-04 "Remove them and continue"). It is never cached from a previous visit. If the cart changed on G-03 and the guest taps "Checkout" again, the new lines and total are what appear; the form values are untouched (§7.7) except that the amount is re-validated (§7.5 rule 8).

### 5.3 Room number (S03)

- C05 label "رقم الغرفة / Room number" — no "(required)" suffix: it is the only required typed field and the form marks optional fields instead.
- F01: typed text 24 px bold so the number is legible at arm's length and matches the "large type" the guest will see again on M-01. Numeric keypad. No placeholder and no example number anywhere near the field, so that no digits other than the guest's own are ever visible in the room-number area (an example like "305" could be mistaken for a pre-filled value).
- C06 error text, one of the four messages in §7.1.
- **Pre-fill from a previous order: No.** F01 is empty on every fresh checkout, even if the device holds a previous order with a room number, because a stale number from an earlier stay pre-filled and confirmed without reading is the most likely way a wrong room reaches staff, while typing 1–5 digits costs two seconds. (The value *is* kept within the current checkout session — Edit cart round-trips, modal closes, reload — per §7.7; that is a draft, not a pre-fill.)
- **Validation against a list of real hotel rooms: No, not in version 1.** The guest interface has no room list, and a mistyped number that happens to exist would pass such a check anyway. What protects the guest is M-01: the typed number is shown in large type and must be confirmed before anything is sent (locked decision 2), and while the order is still New the guest can cancel it from G-06 (locked decision 6) and order again. After submission the room number is shown again on G-05 and on G-06, where it stays readable while the order is still New and can be cancelled (locked decision 6).

**Recorded limitation (open question OQ-01).** Version 1 accepts digits only. A hotel whose room labels contain letters or separators ("A-12", "12B") cannot be served by this field as specified, and the guest sees a wrong-character error that reads as if they mistyped. This is a known, recorded limitation, not an oversight; it is resolved by OQ-01 before build.

**Cross-screen requirement created by this screen (binding on G-05 and G-06 when they are written; those files are not edited from here).** Because G-04 cannot check the typed number against anything, the guest must meet their room number again after submitting, while cancelling is still possible:

- **G-05 Order submitted** shows the room number on its own line, the number at **24 px bold or larger**, Western digits, leading zeros kept, in the same format M-01 used. Copy: `سيُوصَّل طلبك إلى الغرفة {room}` / `Your order will be delivered to room {room}`.
- **G-06 Order tracking** shows the same line in the order's details, and while the status is **New** it is visible in the same view as the "Cancel order" control, so a guest who reads a wrong number has the repair in front of them. Same copy.
- Neither screen may show the room number only inside a collapsed section, a footer, or a line smaller than the order number.
- This requirement is also part of the client-order-key contract (§7.7): it is how a guest discovers that the order the hotel holds carries a value they later corrected.

### 5.4 Notes (S04)

- C07 label "ملاحظات على الطلب (اختياري) / Order notes (optional)".
- F02 text area, rules in §7.2. Notes are order-level, never per product (map §4 decision 4).
- C08 counter "{n}/200", always visible, bold at 200.
- C14 notice "تم اختصار ملاحظتك إلى 200 حرف / Your note was shortened to 200 characters", shown only when a paste was cut to fit the cap (§7.2). It reports what happened to the guest's own text; it blocks nothing.
- No placeholder. No suggestion chips. No error text exists for notes (§7.2); C14 is a notice, not an error.

### 5.5 Payment (S05) and the total

- C09 title "طريقة الدفع عند الاستلام / Payment on delivery".
- B03 Card row and B04 Cash row, stacked, each with its one-line helper. **No option is selected by default**: a defaulted "Card" that a cash-only guest never noticed sends staff to the door with a terminal and no change — an operational error — so the guest must tap one (§7.3).
- When Cash is selected, C11 + F03 (+ C12 on error) appear under the Cash row (locked decision 3). When Card is selected they are hidden and the amount is cleared (§7.4). Nothing about a card type, card number, or online payment appears anywhere; nothing is charged in the browser.
- **The total is restated twice on purpose:** in C04 inside the summary (where the guest reads the lines) and at the end side of B05 (which stays fixed at the bottom while the guest types, so the amount they will pay is visible at the moment they tap "Submit order"). Both show the same value from the same computation: sum over cart lines of qty × unit price as held in the session catalog copy, rounded to two decimals half up — the same rule as G-01 §7.2. There are no fee, tax, tip, service-charge, or discount lines in version 1; the total is exactly the sum of the lines.
- The total also appears inside the "lower than total" message of §7.4, formatted the same way.

### 5.6 Submit bar (S06 / B05)

- Fixed at the bottom; the content scrolls beneath it with 96 px bottom padding so F03 and C12 are never hidden behind it when the keyboard is closed.
- B05 label "إرسال الطلب / Submit order" with the total at the end side. Its behavior is the validation in §7.6 and, on success, M-01.
- While the phone keyboard is open the bar stays fixed at the bottom of the visible area above the keyboard; if the browser instead scrolls the page, that is accepted — the bar must simply be reachable after the keyboard closes.

### 5.7 What is deliberately not on this screen

- No name, phone number, e-mail, or any identity field (locked decision 4: no login, nothing to identify the guest except the room).
- No delivery-time picker, "as soon as possible" toggle, or store-hours notice (map §4 decision 16).
- No per-product notes (map §4 decision 4), no tip, promo code, or coupon field.
- No online payment of any kind; no card details.
- No room list lookup, no room-number dropdown, no floor picker.
- No language toggle, no "My orders" button, no active-order banner (those are G-01's).
- No pre-filled room number from a previous order (§5.3).
- No product images, unit prices, or steppers in the summary (§5.2).
- No toast, no snackbar, no validation summary box at the top: errors are inline under the element they belong to, and the screen scrolls to the first one. C13 and C14 are not exceptions to this rule: both are persistent notices that stay until a stated event removes them, neither fades or auto-dismisses, and neither is a validation summary (C13 reports that nothing was sent; C14 reports what happened to a pasted note).
- No request to the server. Stock was re-checked on G-03 and is re-checked by the submission itself (M-04); prices are the ones in the session catalog copy.

## 6. States

### 6.1 Loading

**G-04 has no loading state.** It sends no request and reads only device data (the cart, the session catalog copy, the checkout draft), so the form is drawn complete on the first frame after navigation. The only wait in the checkout flow happens inside M-01 after "Confirm and send" and is specified in the M-01 file, not here. Consequently there is no skeleton, spinner, or placeholder on G-04.

### 6.2 Empty

**G-04 is never shown empty.** The guard in §3.1 runs on every render: with zero cart lines, or any line marked out of stock in the session catalog copy, G-04 is not drawn and G-03 replaces it in the history. The two ways the cart can become empty "underneath" G-04 are both covered:

1. The guest goes back to G-03 and removes every line: G-03 shows its empty state and its "Checkout" button is disabled, so G-04 is not reachable; if the guest uses the browser's forward gesture to reach G-04 anyway, the guard sends them to G-03.
2. M-04 "Remove them and continue" empties the cart: the map already routes that case to G-03's empty state; the guard is the safety net if a build reaches G-04 first.

### 6.3 Error

There are three error situations on G-04 itself. None shows a toast; none leaves the screen.

1. **Field errors** — a typed or chosen value fails a rule in §7.1, §7.3, or §7.4. The field's border becomes 2 px dark and the inline error text (C06, C10, or C12) appears under it with the exact wording from §7. Several errors can be visible at once. Rules for when they appear and disappear are in §7.6.
2. **Total changed under a typed amount** — the guest typed an amount, went to G-03 and increased the cart (or M-04 reduced it), and the amount is now lower than the new total: C12 shows the "lower than total" message the moment G-04 is rendered again (§7.5 rule 8), before any tap.
3. **Guard failure** (§3.1) — not an error message; G-03 replaces the screen.

**The two notices are not error states.** C13 ("your order has not been sent yet", after M-04) and C14 ("your note was shortened", after a cut paste) report a fact about the order or about a value the guest supplied. No field takes an error border because of them, nothing is blocked, B05 behaves exactly as it does without them, and neither is counted by the validation sequence in §7.6.

Submission failures are **not** G-04 states: connection/server failure is M-03 and out-of-stock rejection is M-04, both specified in their own files. G-04's only duties toward them are stated in §3.1: keep every value, keep the scroll position, rebuild the summary after M-04, and re-validate the amount.

### 6.4 Success

Success on G-04 means: **the guest tapped "إرسال الطلب / Submit order", every rule in §7 passed, and M-01 opened.** Nothing has been sent yet. Exactly:

- The keyboard closes.
- M-01 opens within 100 ms on top of G-04 with the handoff in §7.8.
- C13 and C14, if either is shown, are removed at that moment and the awaiting-resubmission flag is cleared (§7.7). They do not return if M-01 is closed by "Edit room number"; only a later M-04 sets the flag again.
- G-04 stays rendered beneath the backdrop, otherwise unchanged: same scroll position, same values, no error text.
- If M-01 is closed by "Edit room number", G-04 is exactly as it was, with F01 focused (§3.1).

The normal state of the screen before any tap — summary, empty fields, no selection, no errors — is the **form state**; it is what §4 describes and what the wireframe's main frame shows.

## 7. Field rules

Every rule below is a decision. "Trim" always means: remove spaces, tabs, and line breaks at the start and end of the value before validating and before sending.

### 7.1 F01 — Room number (رقم الغرفة / Room number)

| Rule | Decision |
|---|---|
| Required | **Yes.** |
| Input type / keyboard | Single-line text input showing the phone's **numeric keypad with digits 0–9 only** (no decimal point, no minus sign, no letters). |
| Accepted characters | Western digits 0–9 only. Arabic-Indic digits (٠١٢٣٤٥٦٧٨٩) and Extended Arabic-Indic digits (۰–۹), which some Arabic keyboards emit, are **accepted and converted to 0–9 as they are typed**, so the field always displays Western digits. Any other character (letters, spaces inside the value, punctuation, "-", "/", ".") is rejected by validation — it is not silently stripped, so the guest sees why. |
| Length | Minimum **1** digit, maximum **5** digits, counted after trimming. The bounds cover rooms "1" through "99999". |
| Leading zeros | **Kept exactly as typed.** "0305" is sent and shown on M-01, G-05, G-06 and G-07 as "0305", never as "305". The room number is a text value, not a quantity. |
| Spaces | Leading and trailing spaces are trimmed (a pasted " 305 " is "305"). A space inside the value ("3 05") is a wrong-character error. |
| Paste | Allowed; the pasted value goes through the same conversion and validation. |
| Auto-complete / auto-correct | Off. No suggestions above the keyboard. |
| Value sent | The trimmed string, e.g. "0305". |
| Validation fires | Wrong characters and too long: **on blur and on submit**. Empty: **on submit only** (leaving an untouched field empty shows no error until the guest tries to submit). After an error is shown, **every keystroke re-validates** and the error disappears as soon as the value is valid (§7.6). **There is no minimum-length check on blur, and none may be added:** with a minimum of 1 digit the only short value is an empty one, which is checked on submit only. The two blur checks are correct precisely because neither can become valid by typing one more digit — a value with a wrong character stays wrong, and a 6-digit value stays too long. |
| Checked against real hotel rooms | **No** (§5.3). |

Exact error messages — **three, and only three** (shown in C06, one at a time, in this priority order when several apply). There is no "too short" message: a one-digit room number is valid, and the only remaining short case is an empty field, which has its own message.

| Case | Arabic | English |
|---|---|---|
| Empty (after trimming) | اكتب رقم غرفتك | Enter your room number |
| Wrong characters (anything other than 0–9 after conversion) | استخدم الأرقام فقط (0–9) | Use digits only (0–9) |
| Too long (6 digits or more) | رقم الغرفة طويل جدًا: 5 أرقام كحد أقصى | Room number is too long: 5 digits at most |

### 7.2 F02 — Order notes (ملاحظات على الطلب / Order notes)

| Rule | Decision |
|---|---|
| Required | **No.** Optional. |
| Input type / keyboard | Multi-line text area; the phone's **default text keyboard** in the current interface language. The keyboard's "Enter"/"return" key inserts a line break (it does not submit). |
| Accepted characters | Anything the keyboard produces: Arabic, Latin, digits, punctuation, **line breaks, and emoji are all allowed**. |
| Limit | **200 characters** maximum, counted as user-perceived characters: one emoji counts as 1, one line break counts as 1. |
| Counter | C08 "{n}/200" is always visible under the field and updates on every keystroke; at 200 it is shown in bold. It starts at "0/200". |
| At the limit | **Hard cap.** The 201st **typed** character is not entered; nothing else happens (no message, no shake) — the guest can see the typing stop and the counter stand at "200/200". A pasted text longer than the remaining room is cut to fit and **C14 is shown**; the counter reads "200/200". C14 is hidden again on the next change to F02 (any keystroke or deletion) or when M-01 opens. |
| Trimming | Leading and trailing spaces and line breaks are removed before sending. A value consisting only of spaces or line breaks is sent as empty. |
| Auto-correct | The keyboard's own auto-correct is left on (it helps typing in either language). |
| Value sent | The trimmed text, or empty. |
| Validation / errors | **None.** Because the field is optional and hard-capped, there is no error message for notes; no C-element exists for a notes error. **C14 is a notice, not an error:** it does not give F02 an error border, does not block B05, and is not part of the validation sequence in §7.6. |

### 7.4 F03 — Amount you will pay with (المبلغ الذي ستدفع به / Amount you will pay with)

| Rule | Decision |
|---|---|
| Shown | **Only while Cash is selected** (locked decision 3). Selecting Card hides it and **clears its value and any error**, so an amount is never sent with a card order. If the guest returns to Cash the field is empty again. |
| Required | **No.** Optional. Empty means "no change information"; staff bring change as they see fit. |
| Input type / keyboard | Single-line text input showing the phone's **numeric keypad with digits 0–9 only** (no decimal point, no minus sign). The currency label sits inside the field at the end edge as static text and is not typed. |
| Format | **Whole number only. No decimals, no thousands separator, no currency typed.** Banknotes are whole amounts; a guest who will pay with coins that make a fractional amount simply leaves the field empty. |
| Accepted characters | Western digits 0–9. Arabic-Indic and Extended Arabic-Indic digits are converted to 0–9 as typed (same as F01). Anything else — including "." "," and "٫" — is a wrong-character error. |

| Leading zeros | Allowed while typing; on blur the field is rewritten without them ("0100" becomes "100"; "0" stays "0"). |

### 7.5 Summary and total

1. Lines: one per cart line, in cart order, "{qty} × {name}" and the line total = qty × unit price from the session catalog copy, two decimals.
2. Total: sum of line totals, rounded to two decimals half up; identical in C04, in B05, and in the `{total}` of §7.4.
3. Currency label from store settings; Arabic after the amount with a space ("62.50 ر.س"), English before it with a space ("SAR 62.50").
4. Digits: Western 0–9 in both languages, including the quantity and the "×" sign (U+00D7).
5. Quantities are those stored in the device cart (1–10 per line, G-01 §7.1). G-04 never changes them.
6. No fee, tax, tip, discount, or service lines exist in version 1.
7. The summary is rebuilt on every render of G-04 (§5.2).
8. **Re-validation on total change:** whenever G-04 is rendered and the total differs from the total at the previous render in this tab (Edit cart round-trip, M-04 removal), and Cash is selected and F03 is not empty, the "lower than total" rule of §7.4 runs immediately and C12 is shown if it fails. No other field is touched.

### 7.6 Validation sequence and the "Submit order" button

1. **B05 is never disabled for validation reasons.** A disabled button with no explanation would leave the guest guessing which field is wrong; instead, every tap on B05 runs the sequence below and shows the reasons inline. B05 is also never hidden. The only time it does nothing is the 300 ms after a previous tap (rule 7) — and while a modal is open, when its backdrop covers it.
2. On tap: close the keyboard; blur the focused field (which fires that field's blur validation); then validate, in this order: F01 (§7.1), payment choice (§7.3), F03 if Cash is selected and the field is not empty (§7.4).
3. **All** failing elements show their error at once (C06, C10, C12 as applicable); the screen scrolls (animated, 300 ms) so that the **first** failing element's label sits 16 px below the header, and, if that element is a field, focuses it (which reopens the keyboard). If the first failing element is the payment choice, nothing is focused.
4. Once an error is shown on a field, every keystroke in that field re-validates it and removes the error the moment the value is valid; the error does not wait for the next blur or submit. Errors on other fields are unaffected.
5. Blur validation on F01 and F03 (§7.1, §7.4) shows the error but does **not** scroll or refocus.
6. When every rule passes: M-01 opens (§6.4); C13 and C14 are removed and the awaiting-resubmission flag is cleared (§7.7). No value is changed by the validation itself except the visual rewrite of F03's leading zeros on blur (§7.4). The validation sequence never inspects C13 or C14: neither notice can make a submission fail.
7. **Debounce:** B05 ignores further taps for 300 ms after a tap, so a double-tap can never open M-01 twice or run validation twice.
8. Errors are never shown before the guest interacts: on first arrival from G-03 no error is visible, even if the draft is empty. The only exception is §7.5 rule 8 (an amount that a changed total made invalid), which shows C12 on render.

### 7.7 Checkout draft and client order key (what is kept, where, and for how long)

- The four values — room number (raw, as typed), notes, payment choice, amount — form the **checkout draft**. It is saved on the device **as the guest types**, in storage that lives only as long as this browser tab. **The client order key is not part of the draft**: it lives in the device-scoped pending-submission record of the key contract below (rule 7), so that closing the tab destroys the typed values but never the identity of a submission attempt whose outcome is unknown.
- It survives: Edit cart / back to G-03 and return; M-01 "Edit room number"; M-03 "Close" and failed retries; M-04 "Remove them and continue"; a browser reload of G-04.
- Stored with the draft is one more value, the **awaiting-resubmission flag** (one bit): set on the render that follows M-04 "Remove them and continue" when the cart still has ≥ 1 line, cleared when M-01 opens or when the draft is discarded. While it is set, C13 is drawn (§4). Nothing else on G-04 reads it. It is what makes C13 survive a reload, because a guest who reloads the tab in this exact state is the guest most likely to believe the order is already on its way.
- It is **discarded**: on a successful submission (when G-05 opens), and when the browser tab is closed. A new tab starts with an empty draft.
- **"The tab is closed" includes a tab the browser or the operating system discards while it is in the background.** A discarded tab that the browser later restores starts with an **empty** checkout draft: the form is drawn empty, no value is guessed or reconstructed, no payment method is selected, and no error or notice text is shown. The cart itself is unaffected (it is device storage, map §2.3 rule 4), so the summary and the total are drawn from it as on any other render. **The client order key is the one thing that can outlive the tab:** if a submission was sent from the discarded tab and its outcome was never applied, the pending-submission record survives and the restored tab's checkout adopts its key (rules 7–9); if no submission was ever sent from that tab, there is no record and the next checkout generates a new key.
- It is **never carried from one order to the next**: after G-05, the next checkout begins with an empty room number, empty notes, no payment selected, and no amount (§5.3, "no pre-fill").
- The draft is device-only and is never sent anywhere except as part of the submission payload (§7.8).

**Client order key and pending-submission record** (map §4 decision 10). This is one contract spanning G-04, M-01, M-03, M-04 and G-05. It is written here in full and nowhere else; those files reference it and must not state it differently (routing in §7.10).

1. **What the key is, and when it is created.** The key identifies **the submission attempt**, not the values it carries. It is generated **once per checkout session**, the first time B05 opens M-01 — with one exception: if the device holds an **unresolved pending-submission record** at that moment, its key is **adopted** instead of a new one being generated (rule 8).
2. **The key is never replaced because a value changed.** It stays stable for the whole checkout session, across: a cart change made via "Edit cart" or the back arrow, M-01 "Edit room number" and any subsequent edit of the room number, any edit of the notes, a change of payment method, any edit of the amount, M-03 "Close" and every retry, and a browser reload of G-04. Every attempt in one checkout session carries the same key.
3. **The one replacement case: M-04.** The key is replaced with a new one **only when M-04 opens on a stock rejection**, in the same step in which M-04 writes the out-of-stock marks into the session catalog copy (M-04 §3.1). The reason is stated here so that no later revision reads it as a contradiction of rule 2: **a stock rejection is a response the device received and read, in which the server states definitively that no order was created for that key, whereas an edit made after a lost or ambiguous response proves nothing about what the server holds.** Every exit from M-04 — "Remove them and continue", "Back to cart", the backdrop, browser back, and a browser reload — therefore leaves with the fresh key, and no cart change is relied on to replace anything. Nothing else in the product replaces the key, and M-03 never replaces it. A stock rejection **does not delete the pending-submission record** (rule 9): the record survives, the key it holds is replaced with the new key in the same step, and its recorded time of first send becomes the moment M-04 opened. Two things follow, and both are intended: the rejected key is no longer held anywhere on the device and can never be adopted by a later checkout (rule 8), and the 24-hour bound of rule 9 always has a defined start.
4. **The server contract** (a behaviour rule for the technical team, not backend design): *the server never creates a second order for a key it already holds, and it never merges, updates or overwrites the stored order with newly submitted values.* Its success-side response has exactly **three kinds**, named the same way in every file:
   - **`created`** — no order existed for this key; the submitted order was created. Plain success.
   - **`existing-identical`** — an order already existed for this key and the submitted payload is the same order (same lines, quantities, room number, payment method, amount and notes). The stored order is returned, the app treats it as a plain first-time success, and **the guest is told nothing extra**. This is the duplicate-safe retry of map §4 decision 10: a lost response never creates two orders.
   - **`existing-different`** — an order already existed for this key and the submitted payload **differs** from it (the guest corrected something after an ambiguous failure, most often the room number). Nothing is created, nothing is merged or overwritten: the stored order is returned **marked as already existing**, carrying the room number and the status the server holds for it. The app must not treat this as a plain success and must not stay silent (rule 5).
5. **The already-existing case is shown on G-05**, the screen the guest reaches after any accepted submission, in its **already-existing variant**: one persistent notice line directly under the room-number box and above the wrong-number sentence, 14 px, with the same "!" circle icon and no close control, never a toast. G-05 owns and renders this copy; it is reproduced here once so that the contract is readable in one place, and the two strings must stay byte-identical (G-05 §5.2). `{room}` is the room number of the order that exists, in the same format M-01 used (Western digits, leading zeros kept):

   | Arabic | English |
   |---|---|
   | طلبك السابق وصل إلى الفندق بالفعل ولم يتغيّر. الطلب المسجَّل هو للغرفة {room}. لتغييره، ألغِ الطلب من صفحة المتابعة ما دام الفندق لم يقبله بعد، ثم أرسل طلبًا جديدًا. | Your earlier order already reached the hotel and was not changed. The order on file is for room {room}. To change it, cancel it from the tracking page while the hotel has not accepted it yet, then place a new order. |

   The order record saved on the device carries **the status the server returned**, not always New, so G-05 does not promise a cancellation that is no longer available (M-01 §7.4 step 1; G-05 §5.2).
6. Therefore **the order the guest gets back may differ from what they just submitted**, and the guest's correction is never lost silently: they are either deduplicated correctly (`created`, `existing-identical`) or told exactly what exists (`existing-different`). The repair path is the one locked decision 6 already gives: **cancel while the status is New** (M-02 from G-06), then place a fresh order — which is a fresh checkout session with a fresh key. This is why the requirement in §5.3 that G-05 and G-06 show the room number prominently is part of this contract and not a cosmetic choice: it is how the guest discovers which room number the existing order carries.
7. **The pending-submission record — where the key lives.** The key and the minimum needed to recognise the attempt are **device-scoped, not tab-scoped**: they are written to the same device storage as the cart and the order list, never to the tab-scoped checkout draft.
   - **When it is written:** at the moment M-01 sends its request, in the **same synchronous step as M-01's in-flight lock** (M-01 §7.3 layer 1), before any response can arrive.
   - **What is stored, and nothing more:** the client order key the device currently holds; the time of the first send under that key (or, after a stock rejection, the moment M-04 installed it, rule 3); the room number string as sent; the order total; the number of cart lines. The last three exist so that a human reading device state can recognise the attempt. **Nothing in version 1 displays them**, and no guest-facing element on G-04 or anywhere else is created by this rule.
   - **What it survives:** a closed tab, a tab the browser or the operating system discards, a browser restart, and a reload. The checkout draft's tab-scoped lifetime and its no-pre-fill purpose are unchanged by this rule.
8. **A new checkout session adopts an unresolved key.** When G-04 would create a key (rule 1), it first checks the device for a pending-submission record that has not been cleared. If one exists, that record's key is used and no new key is generated; the record's time of first send is kept as it is. This is what protects the guest who force-closed the tab during a submission: the next submission carries the same key, so either the server creates the order (the first request never arrived) or it returns the order that exists, marked already existing, and rule 5's notice tells the guest what happened.
9. **The key and the pending-submission record are discarded together, in exactly three cases:** (a) a success-side response of any of the three kinds in rule 4 is applied (M-01 §7.4, together with the draft, when G-05 opens); (b) the guest ends the checkout session by emptying the cart (the §3.1 guard, "−" to zero on G-03, or M-04 removing the last line); (c) **24 hours after the time of first send recorded in it**, because a key from a previous day describes an order the hotel has long since delivered or cancelled and that staff can see on their own screens. **An M-03 outcome and an M-04 outcome do not clear the record** — those are exactly the attempts that must stay recognisable — and closing the tab does not clear it either; M-04 replaces the key inside the record rather than deleting the record (rule 3). Nothing else discards it.
10. **Residual risk, recorded and not engineered away:** a guest who force-closes the tab **and** empties the cart before ordering again discards the pending-submission record by their own action and can still produce a duplicate order. No machinery is added for this in version 1; it is routed to `/spec/open-questions.md` OQ-01 as a residual-risk item (§7.10).

### 7.8 What G-04 hands to M-01

When §7.6 passes, G-04 opens M-01 and gives it, read-only:

1. The **room number** as the trimmed string (e.g. "0305") — M-01 displays this in large type (its own file specifies how).
2. The **order payload** M-01 will send on "Confirm and send": the cart lines (product identifier, quantity, unit price as held in the session catalog copy), the trimmed notes (or empty), the payment method ("card" / "cash"), the amount (whole number, or none), the total, the current interface language, and the client order key (§7.7).

G-04 does not specify M-01's layout, copy, buttons, or what M-01 does with the response; those are in the M-01 file. G-04 only guarantees that everything M-01 receives has passed §7.1–§7.4 and that the room number shown on M-01 is byte-for-byte the value in F01 after trimming. The key M-01 receives is the stable session key of §7.7 — either the key generated for this checkout session or the key adopted from an unresolved pending-submission record (§7.7 rules 1 and 8). G-04 never hands M-01 a new key because a value changed; the only new key M-01 can ever receive is the one M-04 installed when it opened (§7.7 rule 3). The three response kinds of §7.7 rule 4 (`created`, `existing-identical`, `existing-different`) are M-01's to apply.
