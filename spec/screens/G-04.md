# G-04 — Checkout (إتمام الطلب)

Author: Thinker (Agent 1)
Status: **Draft** (status is changed only by the orchestrator in `/spec/screens-map.md`)
Governing documents: `/CLAUDE.md` locked decisions 1–7; `/spec/screens-map.md` §4 decisions 1–16; conventions set by `/spec/screens/G-01.md` (Western digits 0–9 in both languages; currency after the amount in Arabic "45.00 ر.س" and before it in English "SAR 45.00", two decimals always; tap area of at least 44 × 44 px for every tappable element even when the visible shape is smaller; 14 px minimum body copy).

This is the highest-stakes screen in the product: what the guest types here is what staff carry to a door. Every rule below is written so that a wrong room number, a wrong payment method, or a wrong "amount you will pay with" is caught on the device before it reaches staff.

---

## 1. ID and name

- **ID:** G-04
- **Name:** إتمام الطلب / Checkout
- **Type:** Full guest screen. Reached only from G-03 Cart (and re-shown under the three modals that open on top of it: M-01, M-03, M-04).
- **Language:** the language currently saved on the device (locked decision 7; map §4 decision 12). G-04 has no language toggle; the toggle lives on G-01 and G-08 only.

---

## 2. Purpose

Collect the three things staff need to deliver the cart to the right door — room number, payment method (with the optional cash amount), and optional notes — and hand them to M-01 for the mandatory room-number confirmation.

---

## 3. Entry and exit points

### 3.1 Entry (how the guest arrives)

| From | Trigger | What G-04 shows on arrival |
|---|---|---|
| G-03 Cart | "Checkout" (enabled only when the cart has ≥ 1 line and no line is marked out of stock, map §4 decision 9) | The form (§6.4) scrolled to the top. Summary rebuilt from the device cart. The four form values (room number, notes, payment method, amount) are restored from the checkout draft (§7.7) if the guest already typed them earlier in this tab; otherwise every field is empty and no payment method is selected. The amount, if present, is re-validated against the new total (§7.5 rule 8). No field is focused; the keyboard is closed |
| M-01 Confirm room number | "Edit room number" | Same screen, unchanged scroll position, every value kept. The room number field F01 is focused, the keyboard opens, the cursor sits at the end of the existing value; nothing is pre-selected. No error text is shown until the guest leaves the field or taps "Submit order" again |
| M-03 Order not sent | "Close", or backdrop tap, or "Retry" that failed again (M-03 stays open in that case; G-04 is the screen beneath) | Same screen, unchanged scroll position, every value kept, no field focused. Nothing on G-04 changes because of a failed submission; the failure copy lives in M-03 |
| M-04 Items no longer available | "Remove them and continue", and the cart still has ≥ 1 line | The form scrolled to the top so the rebuilt summary (§5.2) is visible. Every form value kept. The amount, if present, is re-validated against the new total (§7.5 rule 8). No toast; the shorter summary and the new total are the feedback |
| Browser reload while on G-04 | Reload | Same as arrival from G-03: summary rebuilt from the device cart, form values restored from the checkout draft (§7.7), scrolled to the top |

**Guard on every render** (arrival, reload, return from any modal): if the device cart has zero lines, or any cart line is marked out of stock in the session catalog copy (G-01 §5.7), G-04 is not drawn; G-03 replaces it in the history (the guest cannot go "back" to a G-04 that was never shown). G-03 then shows its empty state or its out-of-stock-marked lines. This is why G-04 has no empty state of its own (§6.2).

### 3.2 Exit (where each action leads)

| Action on G-04 | Destination |
|---|---|
| Tap the back arrow (B01) or the browser back gesture | G-03 Cart, with the checkout draft kept (§7.7) |
| Tap "تعديل السلة / Edit cart" (B02) | G-03 Cart, with the checkout draft kept — identical to B01 |
| Tap "بطاقة / Card" (B03) | Stays on G-04; Card selected, Cash unselected; F03 amount field, C11 and C12 hidden; any amount value and amount error cleared |
| Tap "نقدًا / Cash" (B04) | Stays on G-04; Cash selected, Card unselected; C11, F03 (and C12 when it has an error) shown directly under the Cash row; F03 is not focused automatically |
| Tap "إرسال الطلب / Submit order" (B05) with any invalid field | Stays on G-04; keyboard closes; every error is shown inline; the screen scrolls to the first invalid element in the order F01 → payment (B03/B04) → F03 (§7.6) |
| Tap "إرسال الطلب / Submit order" (B05) with every field valid | M-01 opens on top of G-04 with the handoff in §7.8. **The order is never sent from G-04** (locked decision 2); only M-01's "Confirm and send" sends it |
| Guard fails on render (§3.1) | G-03 replaces G-04 |

G-04 never leads to G-05 directly; G-05 is reached only through M-01 (or M-03 "Retry") succeeding, as the map's flow shows. After that success, G-04 is dropped from the history (map §2.3 rule 3).

## 5. Content

### 5.1 Header (S01)

Layout in visual order for Arabic (RTL): [B01 back arrow] … [C01 "إتمام الطلب"] … (empty end edge). In English the arrow flips to the left edge and points left; the title stays centered. There is no language toggle and no "My orders" button on G-04: the checkout keeps one purpose, and both controls are one back-tap away on G-01.

### 5.2 Order summary (S02)

A single bordered box at the top of the form, so the guest sees what will arrive before typing anything.

- C02 title "ملخص الطلب / Order summary".
- One C03 line per cart line, in the order the lines appear on G-03 (the order they were added to the cart; G-04 never re-sorts). Each line: start side "{qty} × {product name}" (14 px; the name in the current language, one line, ellipsis "…" when too long; if the English name is missing the Arabic name is shown in the English interface too, as on G-01); end side the line total = qty × unit price as currently held in the session catalog copy, two decimals, currency per convention. No image, no unit price, no stepper, no remove control: every change to quantities happens on G-03, reached by B01 or B02.
- A 1 px gray rule, then C04 "الإجمالي / Total" with the total (§5.5).
- B02 "تعديل السلة / Edit cart" as the last row, at the end side.
- **All lines are shown**, however many there are; there is no "show more" expander. The screen scrolls.
- The summary is **rebuilt from the device cart every time G-04 is rendered** (arrival, reload, return from M-04 "Remove them and continue"). It is never cached from a previous visit. If the cart changed on G-03 and the guest taps "Checkout" again, the new lines and total are what appear; the form values are untouched (§7.7) except that the amount is re-validated (§7.5 rule 8).

### 5.3 Room number (S03)

- C05 label "رقم الغرفة / Room number" — no "(required)" suffix: it is the only required typed field and the form marks optional fields instead.
- F01: typed text 24 px bold so the number is legible at arm's length and matches the "large type" the guest will see again on M-01. Numeric keypad. No placeholder and no example number anywhere near the field, so that no digits other than the guest's own are ever visible in the room-number area (an example like "305" could be mistaken for a pre-filled value).
- C06 error text, one of the four messages in §7.1.
- **Pre-fill from a previous order: No.** F01 is empty on every fresh checkout, even if the device holds a previous order with a room number, because a stale number from an earlier stay pre-filled and confirmed without reading is the most likely way a wrong room reaches staff, while typing 2–5 digits costs two seconds. (The value *is* kept within the current checkout session — Edit cart round-trips, modal closes, reload — per §7.7; that is a draft, not a pre-fill.)
- **Validation against a list of real hotel rooms: No, not in version 1.** The guest interface has no room list, and a mistyped number that happens to exist would pass such a check anyway. What protects the guest is M-01: the typed number is shown in large type and must be confirmed before anything is sent (locked decision 2), and while the order is still New the guest can cancel it from G-06 (locked decision 6) and order again.

### 5.4 Notes (S04)

- C07 label "ملاحظات على الطلب (اختياري) / Order notes (optional)".
- F02 text area, rules in §7.2. Notes are order-level, never per product (map §4 decision 4).
- C08 counter "{n}/200", always visible, bold at 200.
- No placeholder. No suggestion chips. No error text exists for notes (§7.2).

### 5.5 Payment (S05) and the total

- C09 title "طريقة الدفع عند الاستلام / Payment on delivery".
- B03 Card row and B04 Cash row, stacked, each with its one-line helper. **No option is selected by default**: a defaulted "Card" that a cash-only guest never noticed sends staff to the door with a terminal and no change — an operational error — so the guest must tap one (§7.3).
- When Cash is selected, C11 + F03 (+ C12 on error) appear under the Cash row (locked decision 3). When Card is selected they are hidden and the amount is cleared (§7.4). Nothing about a card type, card number, or online payment appears anywhere; nothing is charged in the browser.
- **The total is restated twice on purpose:** in C04 inside the summary (where the guest reads the lines) and at the end side of B05 (which stays fixed at the bottom while the guest types, so the amount they will pay is visible at the moment they tap "Submit order"). Both show the same value from the same computation: sum over cart lines of qty × unit price as held in the session catalog copy, rounded to two decimals half up — the same rule as G-01 §7.2. There are no fee, tax, tip, service-charge, or discount lines in version 1; the total is exactly the sum of the lines.
- The total also appears inside the "lower than total" message of §7.4, formatted the same way.

### 5.6 Submit bar (S06 / B05)

- Fixed at the bottom; the content scrolls beneath it with 96 px bottom padding so F03 and C12 are never hidden behind it when the keyboard is closed.
- B05 label "إرسال الطلب / Submit order" with the total at the end side. Its behavior is the validation in §7.6 and, on success, M-01.
- While the phone keyboard is open the bar stays fixed at the bottom of the visible area above the keyboard; if the browser instead scrolls the page, that is accepted — the bar must simply be reachable after the keyboard closes.

### 5.7 What is deliberately not on this screen

- No name, phone number, e-mail, or any identity field (locked decision 4: no login, nothing to identify the guest except the room).
- No delivery-time picker, "as soon as possible" toggle, or store-hours notice (map §4 decision 16).
- No per-product notes (map §4 decision 4), no tip, promo code, or coupon field.
- No online payment of any kind; no card details.
- No room list lookup, no room-number dropdown, no floor picker.
- No language toggle, no "My orders" button, no active-order banner (those are G-01's).
- No pre-filled room number from a previous order (§5.3).
- No product images, unit prices, or steppers in the summary (§5.2).
- No toast, no snackbar, no validation summary box at the top: errors are inline under the element they belong to, and the screen scrolls to the first one.
- No request to the server. Stock was re-checked on G-03 and is re-checked by the submission itself (M-04); prices are the ones in the session catalog copy.

## 6. States

### 6.1 Loading

**G-04 has no loading state.** It sends no request and reads only device data (the cart, the session catalog copy, the checkout draft), so the form is drawn complete on the first frame after navigation. The only wait in the checkout flow happens inside M-01 after "Confirm and send" and is specified in the M-01 file, not here. Consequently there is no skeleton, spinner, or placeholder on G-04.

### 6.2 Empty

**G-04 is never shown empty.** The guard in §3.1 runs on every render: with zero cart lines, or any line marked out of stock in the session catalog copy, G-04 is not drawn and G-03 replaces it in the history. The two ways the cart can become empty "underneath" G-04 are both covered:

1. The guest goes back to G-03 and removes every line: G-03 shows its empty state and its "Checkout" button is disabled, so G-04 is not reachable; if the guest uses the browser's forward gesture to reach G-04 anyway, the guard sends them to G-03.
2. M-04 "Remove them and continue" empties the cart: the map already routes that case to G-03's empty state; the guard is the safety net if a build reaches G-04 first.

### 6.3 Error

There are three error situations on G-04 itself. None shows a toast; none leaves the screen.

1. **Field errors** — a typed or chosen value fails a rule in §7.1, §7.3, or §7.4. The field's border becomes 2 px dark and the inline error text (C06, C10, or C12) appears under it with the exact wording from §7. Several errors can be visible at once. Rules for when they appear and disappear are in §7.6.
2. **Total changed under a typed amount** — the guest typed an amount, went to G-03 and increased the cart (or M-04 reduced it), and the amount is now lower than the new total: C12 shows the "lower than total" message the moment G-04 is rendered again (§7.5 rule 8), before any tap.
3. **Guard failure** (§3.1) — not an error message; G-03 replaces the screen.

Submission failures are **not** G-04 states: connection/server failure is M-03 and out-of-stock rejection is M-04, both specified in their own files. G-04's only duties toward them are stated in §3.1: keep every value, keep the scroll position, rebuild the summary after M-04, and re-validate the amount.

### 6.4 Success

Success on G-04 means: **the guest tapped "إرسال الطلب / Submit order", every rule in §7 passed, and M-01 opened.** Nothing has been sent yet. Exactly:

- The keyboard closes.
- M-01 opens within 100 ms on top of G-04 with the handoff in §7.8.
- G-04 stays rendered beneath the backdrop, unchanged: same scroll position, same values, no error text.
- If M-01 is closed by "Edit room number", G-04 is exactly as it was, with F01 focused (§3.1).

The normal state of the screen before any tap — summary, empty fields, no selection, no errors — is the **form state**; it is what §4 describes and what the wireframe's main frame shows.

## 7. Field rules

Every rule below is a decision. "Trim" always means: remove spaces, tabs, and line breaks at the start and end of the value before validating and before sending.

### 7.1 F01 — Room number (رقم الغرفة / Room number)

| Rule | Decision |
|---|---|
| Required | **Yes.** |
| Input type / keyboard | Single-line text input showing the phone's **numeric keypad with digits 0–9 only** (no decimal point, no minus sign, no letters). |
| Accepted characters | Western digits 0–9 only. Arabic-Indic digits (٠١٢٣٤٥٦٧٨٩) and Extended Arabic-Indic digits (۰–۹), which some Arabic keyboards emit, are **accepted and converted to 0–9 as they are typed**, so the field always displays Western digits. Any other character (letters, spaces inside the value, punctuation, "-", "/", ".") is rejected by validation — it is not silently stripped, so the guest sees why. |
| Length | Minimum **2** digits, maximum **5** digits, counted after trimming. Single-digit room numbers are not accepted in version 1 (this is a fixed rule, not a store setting; the bounds cover rooms "10" through "99999"). |
| Leading zeros | **Kept exactly as typed.** "0305" is sent and shown on M-01, G-05, G-06 and G-07 as "0305", never as "305". The room number is a text value, not a quantity. |
| Spaces | Leading and trailing spaces are trimmed (a pasted " 305 " is "305"). A space inside the value ("3 05") is a wrong-character error. |
| Paste | Allowed; the pasted value goes through the same conversion and validation. |
| Auto-complete / auto-correct | Off. No suggestions above the keyboard. |
| Value sent | The trimmed string, e.g. "0305". |
| Validation fires | Wrong characters, too short, too long: **on blur and on submit**. Empty: **on submit only** (leaving an untouched field empty shows no error until the guest tries to submit). After an error is shown, **every keystroke re-validates** and the error disappears as soon as the value is valid (§7.6). |
| Checked against real hotel rooms | **No** (§5.3). |

Exact error messages (shown in C06, one at a time, in this priority order when several apply):

| Case | Arabic | English |
|---|---|---|
| Empty (after trimming) | اكتب رقم غرفتك | Enter your room number |
| Wrong characters (anything other than 0–9 after conversion) | استخدم الأرقام فقط (0–9) | Use digits only (0–9) |
| Too short (1 digit) | رقم الغرفة قصير جدًا: رقمان على الأقل | Room number is too short: at least 2 digits |
| Too long (6 digits or more) | رقم الغرفة طويل جدًا: 5 أرقام كحد أقصى | Room number is too long: 5 digits at most |

### 7.2 F02 — Order notes (ملاحظات على الطلب / Order notes)

| Rule | Decision |
|---|---|
| Required | **No.** Optional. |
| Input type / keyboard | Multi-line text area; the phone's **default text keyboard** in the current interface language. The keyboard's "Enter"/"return" key inserts a line break (it does not submit). |
| Accepted characters | Anything the keyboard produces: Arabic, Latin, digits, punctuation, **line breaks, and emoji are all allowed**. |
| Limit | **200 characters** maximum, counted as user-perceived characters: one emoji counts as 1, one line break counts as 1. |
| Counter | C08 "{n}/200" is always visible under the field and updates on every keystroke; at 200 it is shown in bold. It starts at "0/200". |
| At the limit | **Hard cap.** The 201st character is not entered; nothing else happens (no message, no shake). A pasted text longer than the remaining room is cut to fit, and the counter shows "200/200". |
| Trimming | Leading and trailing spaces and line breaks are removed before sending. A value consisting only of spaces or line breaks is sent as empty. |
| Auto-correct | The keyboard's own auto-correct is left on (it helps typing in either language). |
| Value sent | The trimmed text, or empty. |
| Validation / errors | **None.** Because the field is optional and hard-capped, there is no error message for notes; no C-element exists for a notes error. |

### 7.3 Payment method (B03 Card / B04 Cash)

| Rule | Decision |
|---|---|
| Required | **Yes.** Exactly one of Card or Cash. |
| Default | **None selected.** |
| Behavior | Radio behavior: tapping one selects it and unselects the other; tapping the selected one again changes nothing; there is no way to unselect both once one is chosen. |
| Validation fires | **On submit only.** |
| Value sent | "card" or "cash". |

Exact error message (shown in C10):

| Case | Arabic | English |
|---|---|---|
| Neither option selected when "Submit order" is tapped | اختر طريقة الدفع | Choose a payment method |

C10 disappears the moment B03 or B04 is tapped.

### 7.4 F03 — Amount you will pay with (المبلغ الذي ستدفع به / Amount you will pay with)

| Rule | Decision |
|---|---|
| Shown | **Only while Cash is selected** (locked decision 3). Selecting Card hides it and **clears its value and any error**, so an amount is never sent with a card order. If the guest returns to Cash the field is empty again. |
| Required | **No.** Optional. Empty means "no change information"; staff bring change as they see fit. |
| Input type / keyboard | Single-line text input showing the phone's **numeric keypad with digits 0–9 only** (no decimal point, no minus sign). The currency label sits inside the field at the end edge as static text and is not typed. |
| Format | **Whole number only. No decimals, no thousands separator, no currency typed.** Banknotes are whole amounts; a guest who will pay with coins that make a fractional amount simply leaves the field empty. |
| Accepted characters | Western digits 0–9. Arabic-Indic and Extended Arabic-Indic digits are converted to 0–9 as typed (same as F01). Anything else — including "." "," and "٫" — is a wrong-character error. |
| Length | 1 to **5** digits (maximum 99999). |
| Leading zeros | Allowed while typing; on blur the field is rewritten without them ("0100" becomes "100"; "0" stays "0"). |
| Minimum value | Must be **greater than or equal to the order total** (§5.5). An amount lower than the total **blocks submission** — it is an error, not a warning — because a warning that can be dismissed would reach staff as an instruction to bring change for money that does not cover the order, and the guest's fix is one tap (correct it or clear the field). An amount equal to the total is valid (no change needed). |
| Upper bound | 99999 by length; no other upper check (a very large amount is a real request for change, not an error). |
| Validation fires | Wrong characters and too long: **on blur and on submit**. Lower than total: **on blur, on submit, and whenever G-04 is rendered with a different total** (§7.5 rule 8). After an error is shown, every keystroke re-validates (§7.6). An empty field never errors. |
| Value sent | The whole number (e.g. 100), or nothing when the field is empty or Card is selected. |

Exact error messages (shown in C12, one at a time, in this priority order when several apply). `{total}` is the order total formatted per convention (e.g. "62.50 ر.س" / "SAR 62.50"):

| Case | Arabic | English |
|---|---|---|
| Wrong characters (anything other than 0–9 after conversion, including a decimal point) | استخدم الأرقام الصحيحة فقط (0–9) بدون فواصل | Use whole numbers only (0–9), no decimals |
| Too long (6 digits or more) | المبلغ طويل جدًا: 5 أرقام كحد أقصى | Amount is too long: 5 digits at most |
| Lower than the order total | المبلغ أقل من إجمالي الطلب ({total}). اكتب المبلغ الكامل الذي ستدفعه، أو اترك الحقل فارغًا | This is less than the order total ({total}). Enter the full amount you will pay, or leave this field empty |

Example: total "62.50 ر.س", guest types "60" and leaves the field → C12: "المبلغ أقل من إجمالي الطلب (62.50 ر.س). اكتب المبلغ الكامل الذي ستدفعه، أو اترك الحقل فارغًا". Guest types "100" → C12 disappears on the keystroke that makes the value 100.

### 7.5 Summary and total

1. Lines: one per cart line, in cart order, "{qty} × {name}" and the line total = qty × unit price from the session catalog copy, two decimals.
2. Total: sum of line totals, rounded to two decimals half up; identical in C04, in B05, and in the `{total}` of §7.4.
3. Currency label from store settings; Arabic after the amount with a space ("62.50 ر.س"), English before it with a space ("SAR 62.50").
4. Digits: Western 0–9 in both languages, including the quantity and the "×" sign (U+00D7).
5. Quantities are those stored in the device cart (1–10 per line, G-01 §7.1). G-04 never changes them.
6. No fee, tax, tip, discount, or service lines exist in version 1.
7. The summary is rebuilt on every render of G-04 (§5.2).
8. **Re-validation on total change:** whenever G-04 is rendered and the total differs from the total at the previous render in this tab (Edit cart round-trip, M-04 removal), and Cash is selected and F03 is not empty, the "lower than total" rule of §7.4 runs immediately and C12 is shown if it fails. No other field is touched.

### 7.6 Validation sequence and the "Submit order" button

1. **B05 is never disabled for validation reasons.** A disabled button with no explanation would leave the guest guessing which field is wrong; instead, every tap on B05 runs the sequence below and shows the reasons inline. B05 is also never hidden. The only time it does nothing is the 300 ms after a previous tap (rule 7) — and while a modal is open, when its backdrop covers it.
2. On tap: close the keyboard; blur the focused field (which fires that field's blur validation); then validate, in this order: F01 (§7.1), payment choice (§7.3), F03 if Cash is selected and the field is not empty (§7.4).
3. **All** failing elements show their error at once (C06, C10, C12 as applicable); the screen scrolls (animated, 300 ms) so that the **first** failing element's label sits 16 px below the header, and, if that element is a field, focuses it (which reopens the keyboard). If the first failing element is the payment choice, nothing is focused.
4. Once an error is shown on a field, every keystroke in that field re-validates it and removes the error the moment the value is valid; the error does not wait for the next blur or submit. Errors on other fields are unaffected.
5. Blur validation on F01 and F03 (§7.1, §7.4) shows the error but does **not** scroll or refocus.
6. When every rule passes: M-01 opens (§6.4). No value is changed by the validation itself except the visual rewrite of F03's leading zeros on blur (§7.4).
7. **Debounce:** B05 ignores further taps for 300 ms after a tap, so a double-tap can never open M-01 twice or run validation twice.
8. Errors are never shown before the guest interacts: on first arrival from G-03 no error is visible, even if the draft is empty. The only exception is §7.5 rule 8 (an amount that a changed total made invalid), which shows C12 on render.

### 7.7 Checkout draft (what is kept, and for how long)

- The four values — room number (raw, as typed), notes, payment choice, amount — form the **checkout draft**. It is saved on the device **as the guest types**, in storage that lives only as long as this browser tab.
- It survives: Edit cart / back to G-03 and return; M-01 "Edit room number"; M-03 "Close" and failed retries; M-04 "Remove them and continue"; a browser reload of G-04.
- It is **discarded**: on a successful submission (when G-05 opens), and when the browser tab is closed. A new tab starts with an empty draft.
- It is **never carried from one order to the next**: after G-05, the next checkout begins with an empty room number, empty notes, no payment selected, and no amount (§5.3, "no pre-fill").
- The draft is device-only and is never sent anywhere except as part of the submission payload (§7.8).
- **Client order key** (map §4 decision 10): created the first time B05 opens M-01 in this checkout session, and stored with the draft. It is **replaced by a new key** whenever any value that is part of the order changes after that (a cart line or quantity, the room number, notes, payment method, or amount), so that a retried request always describes exactly the order the guest last confirmed, and a *changed* order can never be treated by the server as a duplicate of the earlier attempt. It is reused unchanged by M-03 "Retry" (which retries the identical payload). It is discarded with the draft on success.

### 7.8 What G-04 hands to M-01

When §7.6 passes, G-04 opens M-01 and gives it, read-only:

1. The **room number** as the trimmed string (e.g. "0305") — M-01 displays this in large type (its own file specifies how).
2. The **order payload** M-01 will send on "Confirm and send": the cart lines (product identifier, quantity, unit price as held in the session catalog copy), the trimmed notes (or empty), the payment method ("card" / "cash"), the amount (whole number, or none), the total, the current interface language, and the client order key (§7.7).

G-04 does not specify M-01's layout, copy, buttons, or what M-01 does with the response; those are in the M-01 file. G-04 only guarantees that everything M-01 receives has passed §7.1–§7.4 and that the room number shown on M-01 is byte-for-byte the value in F01 after trimming.

### 7.9 Sizes, touch targets, and text

- Every tappable element has a tap area of at least 44 × 44 px: B01 (44 × 44), B02 (text button with a 44 px tall tap area), B03 and B04 (72 px tall rows), B05 (56 px), and the three fields (56 / 96+ / 48 px tall, full width).
- Text sizes: C01 18 px; C02, C04, B03/B04 line 1, B05 16 px; F01 typed text 24 px; F02 and F03 typed text 16 px; every label, helper, summary line, and error message 14 px; C08 counter 12 px (a number, not body copy). Nothing on G-04 is smaller than 12 px, and no body copy is smaller than 14 px.
- Fields use 16 px or larger typed text so the mobile browser does not auto-zoom into the field on focus.
- Error text is dark text with a "!" circle icon, never color alone (the wireframe is grayscale and a low-vision guest may not distinguish red).
- Browser zoom and text scaling are never disabled (same rule as G-01 §7.6); the page sets no maximum scale and does not block pinch-zoom on any state of G-04.
- Each field's label (C05, C07, C11) is programmatically associated with its field so that a screen reader reads the label with the field, and each error text (C06, C10, C12) is announced when it appears.
